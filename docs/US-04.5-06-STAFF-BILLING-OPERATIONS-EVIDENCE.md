# US-04.5-06 implementation evidence

Date: 2026-09-10

## Delivered

- Staff billing API under `/api/admin/standalone-billing`, behind the existing `AdminAccessGuard` (control-tower flag, staff role, AAL2, per-request access audit). Writes additionally need `STANDALONE_BILLING_OPERATIONS_ENABLED` and a staff id in `STANDALONE_BILLING_OPERATOR_IDS` (`StandaloneBillingOperatorGuard`), are throttled to 10/min, and every response is `private, no-store`.
- Account list filters (approval, account status, low/zero balance, debt, reconciliation required) applied in SQL before paging, with a per-row billing summary.
- Account detail reconciling the projection with the immutable ledger and held reservations, naming contradictory source rows, and listing held sends, purchases, provider-event summaries, the ledger and org-scoped staff audit history.
- Signed credit adjustments (preview → apply) bound to a server fingerprint of the account state, with `Idempotency-Key`, one transaction for lock, ledger entry, projection and audit.
- Tenant-checked resolution of outcome-unknown credit sends through the existing resolver; its audit row now also records organization, evidence and request id.
- Forced Paymob inquiry for pending or flagged purchases using stored identifiers only.
- Refund and chargeback evidence recorded through the canonical purchase state machine with a new `staff_evidence` source that can never grant or settle a payment.
- Projection repair (preview → apply) that rebuilds only the projection from ledger and held reservations under lock and refuses contradictory sources.
- `CreditAccountingRepository.postLedgerEntry`: one posting primitive now used by purchase grants, purchase reversals and staff adjustments.
- Staff console pages: filtered list, account detail with timelines, and confirmed operation panels and dialogs in English and Arabic.
- [Operations runbook](STANDALONE_BILLING_OPERATIONS_RUNBOOK.md) and environment documentation.

No database migration was required: every constraint the operations rely on (immutable ledger, account version guard, reservation state guard, `guard_credit_ledger_source`, composite tenant foreign keys, `staff_adjustment` actor requirement) already exists from `0032_credit_and_payment_domain_foundation.sql`.

## Decisions and assumptions

These were agreed or chosen during implementation and need no code change to revisit, except where noted.

1. **Writes need a flag and a named-operator allowlist** (agreed). Reads and previews need only the staff role.
2. **Refund evidence takes the cumulative refunded total** (agreed), matching the state machine, so a real refund callback arriving later carries no new money.
3. **Dual control is not enforced.** The operator who takes a preview applies it. The runbook records the finance-side procedure; enforcing a second approver is a follow-up if finance requires it.
4. **Adjustments are bounded to ±10,000 credits** and refused for accounts pending approval.
5. **Contradictory source rows block every staff write, including repair.** They need engineering; rebuilding from them would pick a side.
6. **Staff evidence is stored as provider `akeed_staff`, `verified = false`.** Partial disputes are quarantined with `dispute_amount_mismatch`, because the ledger treats a dispute as all-or-nothing.
7. **Unknown request fields are dropped, not rejected.** The application's global `ValidationPipe` whitelists before the controller's `forbidNonWhitelisted` pipe runs, so a body carrying `status: "successful"` or a quantity reaches no service. The controller spec asserts this. Rejecting them outright would mean changing the global pipe for every route.
8. **Detail timelines show the latest rows** (ledger and holds 100, purchases, events and audit 50) with a truncation note. Cursor paging can follow if accounts outgrow it.
9. **Chargebacks still have no Paymob source** (US-04.5-04 item 6). Staff evidence is the only chargeback path until a sandbox capture exists.

## Found while implementing

- **The application did not boot at the start of this story.** `BillingModule` used `DualAuthGuard` without importing `AuthModule`, so Nest could not resolve `TokenValidatorService`. Fixed separately in `fix(billing): import AuthModule so the billing module boots`. After the fix, a real `AppModule` boot registers the eleven staff billing routes and exactly one Paymob callback route.
- **Three existing PostgreSQL contract suites fail identically before and after this story** (verified on a worktree of `5929e93`):
  - `test:contract:paymob-checkout`: 12 of 29 fail. The fake payments port defaults every event to `providerTransactionId: 'txn-1'`, so the second purchase in the schema violates `payment_purchase_transaction_key`. The US-04.5-04 evidence records that this suite had never been run against a database.
  - `test:contract:credit-usage`: 1 of 17 fails (`records receipts for a salvaged ambiguous send without moving credits` expects one row and receives none).
  - `test:contract:standalone-approval`: 1 of 11 fails (the approved source's `billing_plan_id` / `billing_status` are `null` where the test expects `starter` / `not_required`).

  They are not changed here; they belong to their own stories' follow-ups.
