# US-04.5-04 implementation evidence

Date: 2026-09-09

## Delivered

- Merchant billing APIs at `/api/billing/*`: credit summary, ledger, purchase history, purchase detail and purchase creation. Organization, actor, price, currency, provider and mode are all derived server-side; the request contributes a quantity and nothing else, and a body carrying its own price or status is rejected rather than stripped.
- `PaymobPaymentsAdapter` behind `PAYMENTS_PORT`, the only class that knows Paymob's HTTP surface. Create Intention is one bounded attempt; inquiry is the retrying call because it creates nothing.
- Paymob processed-callback HMAC over the twenty documented fields, with a shape check before any crypto and a timing-safe comparison of equal-length buffers.
- A canonical purchase state machine as a pure function, and one transaction that persists the provider event, transitions the purchase, posts the ledger entry and updates the account projection together.
- Inquiry recovery that feeds provider answers through the same ingestion path a callback takes, with a matching fingerprint so a recovered callback and the real one cannot both grant.
- Refund, partial-refund and chargeback accounting boundaries, with anything that is not a whole-credit reversal recorded for staff instead of guessed at.

## No migration

Every column, index, constraint and trigger this story needs already exists from `drizzle/0032_credit_and_payment_domain_foundation.sql`: the purchase terms and their immutability trigger, the three provider identifiers with per-provider partial uniques, `checkout_expires_at`, `refunded_minor`, the full `reconciliation_*` set, `payment_event_fingerprint_key`, `credit_ledger_purchase_key`, `credit_ledger_reversal_source_key`, `guard_credit_ledger_source`, and the two history indexes the cursors walk. `credit_accounts` has no non-negative check on `posted_balance`, so debt is representable as shipped. Only new query methods were added.

## Exactly-once, and where it is enforced

None of the following is application logic:

| Guarantee | Enforced by |
| --- | --- |
| A redelivered provider fact changes nothing | `payment_event_fingerprint_key (provider, fingerprint)` |
| One grant per purchase | `credit_ledger_purchase_key (purchase_id) where type='purchase'` |
| One ledger entry per key per organization | `credit_ledger_idempotency_key` |
| One reversal per purchase, type and provider reference | `credit_ledger_reversal_source_key` |
| A reinstatement matches its chargeback reversal exactly | `guard_credit_ledger_source` |
| One Paymob intention per Idempotency-Key | `payment_purchase_request_key` plus skipping the provider call on a duplicate |

The fingerprint is derived from provider facts alone and never from the arrival channel. That is what makes recovery safe: an inquiry result and the callback for the same transaction produce the same fingerprint, so the second is a proven replay.

## Assumptions and deliberate departures

These need a human decision before the release gate; none of them is hidden in the code.

1. **A replay returns no checkout URL.** The URL embeds the intention client secret, and AC5 requires the secret not to be exposed after its short-lived use, so it is never persisted. An idempotent replay therefore answers `checkoutUrl: null` with `CHECKOUT_URL_ALREADY_ISSUED`, and a fresh attempt needs a fresh `Idempotency-Key`. The alternative — encrypting the secret at rest, or caching it in Redis — keeps a live payment credential around and was not taken.
2. **A verified but unsupported event type answers 202, not 4xx.** Nothing changes and nothing is granted, but a 4xx would have Paymob redelivering it forever with no possible different result.
3. **A frozen credit account also answers 202.** This is a narrow departure from "non-2xx on a database failure": a projection that no longer matches its ledger will not resolve by being retried, and a provider hammering it buries the alert. Transient database failures still escape as 5xx so the provider retries.
4. **Inquiry is lazy.** The merchant's own polling of `GET /api/billing/purchases/:reference` drives recovery, rate limited by the purchase's own `next_reconciliation_at`. No scheduler was added; the method is exported for the staff console and a future queue processor.
5. **`billing_data` sent to Paymob is fixed placeholders.** A credit top-up has no customer, so no merchant personal data is handed to a payment processor. Paymob must confirm placeholders are accepted on both card and wallet integrations.
6. **Chargebacks have no Paymob source yet.** The state machine, the ledger and the ingestion path all handle dispute signals and are covered by tests, but `paymob-status.mapper.ts` deliberately does not invent a dispute payload shape it has not seen. Wiring the source belongs to US-04.5-06 once a sandbox capture exists.
7. **Integration identifiers are sent as configured strings.** If the real Paymob ids are numeric-only, tighten the already-shipped config parser.
8. **No debt ceiling.** The epic permits debt and bounds nothing; a chargeback on a 5,000-credit purchase creates 5,000 credits of debt.

## Provider dependency

Akeed's Paymob merchant account is not enabled, so the callback fixtures in `src/infrastructure/spokes/paymob/fixtures/` are **synthetic** and no live provider call was made. Two things follow:

- The HMAC spec compares `buildPaymobHmacSource` against a second, longhand statement of the documented field order written inside the spec, rather than against the same list the implementation reads. Reordering the production list fails that comparison whether or not a real digest exists.
- Each fixture carries a `provenance` marker and a slot for the digest Paymob actually sent. A fixture marked `sandbox-capture` is verified against its own recorded digest using `PAYMOB_FIXTURE_HMAC_SECRET`; without that variable the block skips with a `NOT RUN:` message. `fixtures/README.md` documents the swap, and the specs must then pass unchanged.

Absent/null handling, boolean serialization and the wallet callback shape are provider contract details that stay unverified until that capture. Paymob must still supply matching test/live keys, the HMAC secret, enabled card and mobile-wallet integration ids, Vodafone Cash availability, Unified Checkout, callback configuration on **both** integration records, and inquiry/refund access.

## Rollout

Deploy with `STANDALONE_CREDIT_BILLING_ENABLED=false`. Nothing in this story is reachable: the merchant APIs answer `BILLING_DISABLED`, the callback guard rejects for want of a configured secret, and no `PAYMOB_*` value is read. Enabling it makes every `PAYMOB_*` variable required and validated at startup, where a placeholder value or a sandbox-looking hostname in live mode aborts boot rather than reaching a payment.

Configure the processed callback on both the card and the mobile-wallet integration records; the per-intention `notification_url` is sent as well but Paymob documents it as card-only. Do not enable Vodafone Cash traffic until a wallet callback has been captured in sandbox.

Rollback is the same flag in reverse. Purchases, events, ledger entries and account projections are all preserved; only new checkouts and new holds stop.
