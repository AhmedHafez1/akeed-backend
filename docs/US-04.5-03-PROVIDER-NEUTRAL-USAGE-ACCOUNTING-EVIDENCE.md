# US-04.5-03 implementation evidence

Date: 2026-09-09

## Delivered

- Provider-neutral usage accounting routes Shopify through periodic-plan accounting and Standalone through prepaid credits.
- Standalone claims lock the tenant credit account, create one dispatch reservation per generation, and preserve holds for ambiguous provider outcomes.
- Accepted initial and follow-up messages consume one credit each. Confirmed rejection releases a hold; confirmed post-acceptance delivery failure reverses consumption exactly once.
- Duplicate claims, acceptances, callbacks and staff resolutions reload canonical state. New retry generations are eligible only after release or reversal of the previous generation.
- Credit-aware action checks use the established denial codes in backend APIs and Arabic/English frontend surfaces while preserving access to existing records.
- Dispatch accounting mode is persisted by migration `0033` so historical callbacks cannot switch billing systems.

## Cutover and rollback

Enable Standalone credit billing only through the existing feature configuration after legacy in-flight sends have drained. Unresolved legacy unknown sends block new prepaid claims; their callbacks continue to use the persisted historical accounting mode. Roll back by disabling the feature flag and reverting the application commits before applying migration `0033`; no production migration, deployment or provider call was performed for this implementation.

Live Meta validation remains a separate release-gate dependency and is intentionally not included in local validation.

## Post-review fixes — 2026-09-09

A review of the shipped story found five defects. All are fixed in the commits below.

### Corrections to the validation recorded above

- `npm run test:acceptance:e04` did **not** pass. `5362181` added
  `import ... from 'contracts/usage-accounting-fixture'` — a bare specifier Jest
  cannot resolve — so the suite reported "Test suite failed to run" and its
  result was mistaken for a pass. Restoring it exposed three further contract
  drifts predating this epic (`64482b5`, `d6b70ba`) and one stale assertion.
- `npx tsc --noEmit` over the whole project did not pass either, for the same
  file. `npm run build` (`tsconfig.build.json`) excludes `test/` and was green,
  which is why the difference went unnoticed.
- The contract, unit, structured-log, build and frontend results stand.

### Defects fixed

1. **Standalone sends broke on deploy, not on enablement.** `UsageAccountingRouter.mode()`
   ignored `STANDALONE_CREDIT_BILLING_ENABLED`, so every Standalone source routed to
   prepaid credits the moment the code landed and was denied downstream with
   `PAYMENT_PENDING_RECONCILIATION`. The story ships the router dark; disabling the flag
   now restores the E04 periodic plan instead of blocking. Settlement still follows the
   `accounting_mode` persisted by migration `0033`, so holds taken before a rollback
   consume, release and reverse through credits, and the periodic claim path refuses a
   row already bound to credits rather than billing it twice.
2. **Prepaid delivery receipts stalled the Meta status webhook.** `recordProviderStatus`
   threw for any prepaid dispatch that was not `accepted`. A send salvaged at
   `outcome_unknown` keeps its provider message id, so Meta reports on it; the throw
   escaped a handler with no per-status recovery, abandoning the rest of the batch and
   making Meta retry indefinitely. Receipts are now recorded for `outcome_unknown`
   without moving credits — the hold stands until staff resolve it.
3. **Real failures were disguised as reconciliation conflicts.** `PrepaidCreditAccounting.lock`
   caught every error, including transport failures, and discarded the invariant report.
4. **`resolveNotAccepted` carried its own monthly-usage decrement**, which no-ops where
   `PeriodicPlanAccounting.release` raises.
5. **Three port declarations were unimplemented and uninjected**, one of them colliding by
   name with the concrete router class.
