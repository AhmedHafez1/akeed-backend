# Customer change-request messaging

Change requests default to off. `PATCH /api/settings` and `PATCH /api/onboarding/settings` accept `changeRequestsEnabled` through the existing settings DTO. The owner/admin checks and tenant selection are unchanged. Settings state includes `changeRequestsEnabled` and `changeRequestReadiness` (`ready` and per-language/style/sender `variants`). A blocked activation returns `CHANGE_REQUEST_TEMPLATES_UNAVAILABLE` with readiness details. Settings changes while enabled are checked again.

The ordinary template selector excludes change-request versions. After normal language/style and sender selection, an opted-in send can use the exact approved three-button counterpart. Missing or unusable counterparts retain the ordinary two-button selection; they never cause another language/style or sender to be selected to obtain a third button. The dispatch snapshots its button capability, cycle and recipient digest. Disabling future use does not revoke already-sent valid buttons.

## Template preparation and approval

Migration `0093_change_request_messaging.sql` prepares drafts for every registered text confirmation/reminder variant, including draft-only supported languages. Each draft points to its predecessor through `change_request_of_key`. No existing definition, default, provider ID or approval is changed. Prepared content should be reviewed through the existing template-authoring workflow before submission. The draft editor, preview and submission review include all three buttons and the immutable predecessor relationship. Admin > Templates > Request a change preparation reconciles missing counterparts and exports the review. Reconciliation preserves existing operator work; migration seeds must be checked against synchronized provider content and parameter mappings.

Use existing authorized staff template submission, reconciliation, sync and activation operations to provision the shared sender. Activate counterparts without making them ordinary language defaults or retiring their predecessors; selection stays controlled by merchant opt-in. Approval must come from actual provider metadata, with compatible variables and exactly three quick replies: Confirm, Cancel, Request a change. Arabic uses `طلب تعديل`. Once a shared version is approved and active, the existing merchant connection provisioner copies all three buttons and waits for independent approval in each merchant account. A merchant connection with pending, rejected, paused, drifted or non-utility copies is unavailable for three-button use. Shared-number image twins are reviewed through the existing image-twin workflow after text approval. Three-button branded sends require the approved, synchronized image twin of that exact three-button text parent. An ordinary two-button image twin cannot stand in for it. Merchant-owned numbers continue using independently approved text copies only; saved logos do not block their text readiness.

Provider requirements were checked against [Meta template components](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/components.md): quick-reply labels allow 25 characters; button indexes define their order. A local definition is never evidence of approval.

## Incoming actions and acknowledgements

Versioned buttons carry the verification and confirmation cycle, and must quote their accepted outbound message. The receiving account/number, tenant, order, recipient digest and cycle are checked. Customer choices are serialized under the verification lock and ordered by provider timestamp, with event identity as the deterministic tie-breaker. Existing terminal-state protections remain. Legacy callbacks remain supported; messages without valid associations are not used to discover a merchant for this feature.

Opening a request commits its history and durable side effects before delivery. Customer acknowledgement, merchant email and platform-marker effects have independent consumers. An acknowledgement uses fixed localized copy, the original confirmation dialect and sender, and store/order identifiers. It bypasses quiet hours independently of reminder and resend scheduling and independently of ordinary thank-you settings.

`change_acknowledgment` is a separate dispatch kind, scoped to the request's confirmation cycle. It consumes one message through existing sender-specific credit or plan accounting. No new price, ledger or Meta free allowance is introduced. Exhausted allowance permanently settles the effect as `skipped_no_allowance`; later top-ups do not revive it. Closed service windows skip the reply without a template fallback. Unknown provider outcomes are parked for existing reconciliation rather than blindly sent again. Receipts update billing and acknowledgement delivery state without changing the order outcome.

The existing verification-automation queue sweeps recoverable acknowledgement effects once per minute. Immediate handling runs after request capture; the sweep covers process/queue interruption. Both paths share the same effect lease and logical dispatch identity.

## Merchant handling

The merchant's outcomes, the dashboard queue and the updated confirmation are described in [Order Confirmation Workflow](ORDER_CONFIRMATION_WORKFLOW.md#merchant-handling-of-a-change-request). An updated confirmation is an ordinary confirmation of the next cycle: it uses the three-button template only while the store is opted in and ready, it is charged as one confirmation, and it waits for quiet hours.

## Merchant email and platform updates

Each new request schedules one immediate `verification.change_request_effects` job on the existing verification-automation queue. The existing minute sweep also recovers committed effects after a queue/process interruption. Email uses `EMAIL_PORT` (Resend), the store's usable notification email or the existing account-owner fallback, and the existing notification language convention (`defaultLanguage`, Arabic for `auto`). It includes store, order, source, request time in the store timezone and a contact-before-shipping instruction. Standalone links open the authenticated confirmations route with `open=<verificationId>`; sign-in retains that internal destination. Shopify links enter the app through Shopify Admin. Neither link grants order access.

Email uses the existing `EMAIL_ALERTS_ENABLED`, `RESEND_API_KEY`, `EMAIL_FROM` and `FRONTEND_DASHBOARD_URL` configuration; Shopify navigation also uses the existing `SHOPIFY_API_KEY`. Missing recipients, disabled email and provider failures are recorded on the effect and exposed in the request view. The request stays actionable. Merchant email never calls WhatsApp sending, reservations or usage accounting. There is no notification-address setting, email reminder or merchant WhatsApp alert.

The first provider attempt freezes the complete envelope and a request-specific idempotency key. Transient failures use bounded durable retries with exponential backoff. A new confirmation cycle can create a new request and notification; duplicate taps/jobs cannot. `done` means provider acceptance, not inbox delivery. Retries retain the exact payload, including the sender address. Replays stop before [Resend's 24-hour idempotency window](https://resend.com/docs/dashboard/emails/idempotency-keys) expires; an older uncertain attempt becomes `email_outcome_unresolved` and requires provider reconciliation instead of another automatic send.

Shopify reconciliation uses the existing outcome registry/tracker and targeted GraphQL tag mutations. `Akeed: Change Requested` replaces the explicit Akeed status tags while open. Current customer/merchant outcomes replace it with the appropriate existing status tag; successful reconfirmation clears obsolete Akeed status tags. Other tags, including merchant tags and `Akeed: Test`, are preserved. Per-order leases, claim tokens, revisions, checks before writes and checks after provider responses make stale work retry against current state. Failed writes remain in the existing remote-sync status/retry controls. No fulfillment hold or permission is added.

WooCommerce and EasyOrders have no native request-marker capability: those effects are skipped, while their existing outcome mappings, settings and provider recovery remain authoritative for both customer and merchant actions. Standalone applies local lifecycle behavior with no external calls. Salla and Zid remain reserved, unimplemented types. Existing source-update handlers treat reflected outcomes as observations; Shopify order-update jobs remain unhandled. Updates cannot resolve requests or retrigger notifications.

Migration `0095_change_request_notifications.sql` adds retry/envelope fields to the existing outbox and revision/lease fields to existing sync rows. Apply it through normal migration delivery before running the new readers/workers. Rollback must retain the consumers and persistence for already captured requests.

For recovery, use the request's tenant-scoped email status/reason and the order's existing remote-sync retry action. After correcting configuration or a missing recipient, support may return an email effect that has **never attempted provider I/O** (`first_attempt_at IS NULL`) to pending for sweep recovery. Preserve the frozen payload/key of every attempted email; an expired uncertain attempt needs provider investigation. Never replay an accepted initial email or create a new logical notification for a technical retry.
