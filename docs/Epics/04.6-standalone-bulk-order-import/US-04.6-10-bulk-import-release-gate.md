## User story and value

As the product owner, I want evidence that bulk import handles real merchant spreadsheets, never double-sends or over-bills, and doesn't hurt WhatsApp quality, so that we can enable it for all Standalone merchants.

**Business value:** This is the go/no-go decision, based on recorded evidence rather than assumption.

## Scope

- The fixture pack.
- End-to-end and concurrency suites.
- The manual/bulk equivalence proof.
- Regression of existing paths.
- The pilot with real merchants.
- The quality-rating review.
- The go/no-go record.

**Out of scope:** New features discovered during the pilot; these become follow-up backlog items.

## Acceptance criteria

1. A committed fixture pack under `test/fixtures/order-imports/` contains the files below. Each has an expected-outcome manifest (per-row outcome and issue codes):
   - `arabic-excel.xlsx` (Arabic headers, number-formatted phones, a hidden first sheet, merged cells, formulas, serial dates)
   - `unicode-text-utf16le.txt` renamed to `.csv` (tab-separated)
   - `windows-1256.csv`
   - `semicolon-eu.csv`
   - `utf8-bom-multiline-quotes.csv`
   - `shopify-orders-export.csv` (line items spread across rows, `Name` as `#1001`, payment gateway column)
   - `no-reference.csv`
   - `mixed-payments.csv`
   - `old-and-future-dates.xlsx`
   - `5000-rows.csv` and `5001-rows.csv`
   - `101-columns.csv`
   - `zip-bomb.xlsx`
   - `protected.xlsx`
   - `macro.xlsm`
   - `legacy.xls`
   - `pdf-renamed.csv`
   - `formula-injection.csv`
   - `scientific-phones.xlsx`
2. An automated end-to-end test (backend integration plus Playwright) runs upload → map → review → commit → start → release → confirm/cancel webhook → results export for `arabic-excel.xlsx`. It asserts that the results CSV matches the manifest and that no message is sent before start.
3. **Equivalence proof:** for the same order data, a manual order and an imported order produce identical verification rows (except IDs and timestamps), identical dispatch ledger kinds, identical credit consumption, identical follow-up/no-reply scheduling and identical dashboard lifecycles. `VerificationHubService` and the send services contain no import-specific branch (a static check). An architecture check proves the adapter boundary: `order-imports` and `orders` reach persistence and dispatch only through `StandaloneOrderIngestionService` (or the release scheduler), and no code under `verification-core`, the normalizers or the eligibility strategies reads `ingestionType`. A second static check proves every row of the epic Reuse map: no duplicated currency list, idempotency-key regex, totalPrice pattern, `PhoneNumberUtil` instance, `findActiveByOrg` source check, direct `resolveDenial`/`hasAvailableSlot` call outside `StandaloneSendReadinessService`, second ingestion repository or second download helper.
4. **Concurrency suite:**
   - double commit;
   - two batches with overlapping references;
   - stop against a release tick;
   - a balance drop during release;
   - a worker kill during commit and during release.

   Each proves at most one order per reference, at most one dispatch per event, and zero billing for withdrawn events.
5. **Regression:** the E04 manual-order suite, the E04.5 billing suite and the E01 Shopify characterization gates all pass unchanged after the `StandaloneSendReadinessService` extraction and the predicate change.
6. **Performance:**
   - Upload of 5,000 rows to preview in under 10 s p95 on staging.
   - Commit of 5,000 rows in under 60 s.
   - Exports in under 5 s.
   - Release lag under 60 s from the planned tick outside quiet hours.
7. **Pilot:** at least 3 real Standalone merchants import at least one real file each, with the flag enabled for their organizations only. Recorded per merchant:
   - file format and encoding;
   - rows by outcome;
   - mapping corrections made;
   - support contacts;
   - time from upload to start;
   - confirmation rate against manual orders.
8. **Quality review:** during the pilot and for 7 days after, the WhatsApp phone-number quality rating and template status are checked daily. Block/report signals on imported orders must not exceed those on manual orders. Any rating drop blocks general availability until it is explained and pacing or policy is adjusted.
9. The go/no-go record is appended to this story with date, build, commands, results, known limitations and the decision. It includes a decision on each ASSUMPTION in the epic (pacing rate, the 7-day age window, the duplicate windows, the 72-hour start window). The root README status is updated only after a "go".

*Decisions confirmed with the product owner before coding:*
- **Results are the existing Verifications table.** The E2E "results" step is `GET /api/verifications?importBatchId=` (the same list used for manual, CSV and every future source), plus `GET /:id/rows` for rows that did not import. No `results.csv`, which stays deferred with US-04.6-08.
- **Playwright** is a new frontend devDependency (`@playwright/test` 1.63.0, exact). It drives the real wizard and Verifications UI inside the `test/e01-smoke` fixture app, replaying the answers the real backend gave in the PostgreSQL E2E. An authenticated walkthrough against a running backend is a pilot hand-off.
- **Allow-list:** `enabled = STANDALONE_BULK_IMPORT_ENABLED && (BULK_IMPORT_PILOT_ORG_IDS is empty || orgId ∈ list)`. An empty list means general availability.
- **Real merchant samples:** none were provided. Every fixture is synthetic, so the "real file shapes" ASSUMPTION stays open. No sample was invented.

*Defects the gate uncovered and fixed (each owned by the story that introduced it):*
- **D1: the row validator broke the adapter boundary** (owner [US-04.6-04](US-04.6-04-row-normalization-validation-and-dedupe.md), which added it; recorded as a hand-off in [US-04.6-06](US-04.6-06-idempotent-commit-into-held-orders.md) evidence item 3). `validation/row-validator.ts` imported `buildStandaloneOrderEnvelope` directly, so a channel was building the envelope. New `order-ingestion/standalone-order-preview.ts` exposes `previewCanonicalOrder(channel, order)`, which returns the same `canonicalOrder` through the one envelope builder. This is the local refactor US-04.6-06 suggested; a pure helper rather than a `previewEligibility` service method, because the validator is pure and the eligibility evaluator is already injected. Outcomes are unchanged: every validator spec and the manifest suite pass as before. The new architecture check pins that only the ingestion service, the preview helper and the envelope module reference the builder.
- **D2: a committed batch's detail page failed on PostgreSQL** (owner [US-04.6-07](US-04.6-07-start-confirmation-checkpoint-and-paced-release.md)). `OrdersRepository.countLifecycleByImportBatch` grouped by a parameterized expression, which Postgres rejects ("must appear in the GROUP BY clause"), so `GET /api/order-imports/:id` answered 500 for every batch once committed. Unit tests mock the repository, so only the new Postgres E2E reached it. It now groups by position (`groupBy(sql\`1\`)`), with a comment saying why.
- **G5: the E04.5 contract script raced PostgreSQL start-up** (tooling, owner E04.5). `scripts/test-e045-contracts.ps1` checked readiness over the Unix socket, which is up before TCP, so the first `psql` over TCP sometimes failed ("psql socket", 2 of 3 baseline runs). The readiness check now uses `pg_isready -h 127.0.0.1`, as the new wrappers do.

*Gate observations (recorded, not changed):*
- **G1: `الهاتف` was not a phone alias.** In `unicode-text-utf16le.csv` and `windows-1256.csv` the phone column was not auto-mapped, so the merchant had to map it by hand. It is not a gate defect. It was handed to a follow-up for the alias dictionary ([US-04.6-03](US-04.6-03-column-detection-mapping-and-saved-profiles.md)), which has since added `الهاتف`/`هاتف` (dictionary version 2) in this working tree and set both manifests to `autoMapped: true`.
- **G2: regenerating fixtures changes `styles.xml` in every XLSX.** SheetJS keeps a global number-format table, so the new date formats appear in older workbooks too. Cosmetic: every parser test and expected grid is unchanged.
- **G3: the parser trims a leading tab or CR.** In `formula-injection.csv`, `\tcmd` and `\rcalc` arrive as `cmd` and `calc`. They are harmless either way (no leading `= + - @`), and the manifest records what the parser really returns.
- **G4: the catalogue and US-04.6-04 AC4 disagree on `1.250,00`.** The catalogue calls it ambiguous; AC4 (the governing story) reads the last separator as the decimal, so it is 1250.00. `12,3456` is `AMOUNT_AMBIGUOUS`. The traceability entry D-06 records this.
- **Existing idempotency-key regex copies** in `admin/billing-observability.service.ts` and `admin/standalone-billing-operator.guard.ts` (E04.5 staff tools, outside the order channels). The reuse-map check allow-lists them by name, and they are flagged for a follow-up.
- **Local commit time is over its target** (see AC6): 70.6 s p50 for 5,000 rows against 60 s. Staging must confirm it; if staging also misses, the owner is US-04.6-06 (commit processor).

- The 19 AC1 files each have a `<file>.manifest.json` generated by the same script. It records the mapping and options, a fixed `now`, the store timezone and either a `fileError` code or the expected rows.
