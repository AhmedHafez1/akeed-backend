## User story and value

As a merchant, I want clicking Import to create my orders exactly once, even if I double-click, refresh or lose my connection, so that I can trust the numbers I see and never create duplicate orders.

**Business value:** Import becomes a durable, retry-safe state promotion that reuses the proven manual-ingestion guarantees instead of a second order-creation path.

## Scope

- The commit endpoint and its idempotency.
- A background chunked commit job.
- A bulk variant of the ingestion repository.
- Commit-time dedupe re-check.
- Progress reporting.
- Crash recovery.
- The imported/awaiting-start screen.

**Out of scope:** Starting confirmation (US-04.6-07).

## Acceptance criteria

1. `POST /api/order-imports/:id/commit` requires `Idempotency-Key` and an owner/admin. The key is validated by the shared `src/shared/validation/idempotency-key.ts`, extracted from the private `OrdersService.normalizeIdempotencyKey`. Manual orders keep their codes through a caller-supplied code map; the import uses `IMPORT_IDEMPOTENCY_KEY_REQUIRED` and `IMPORT_VALIDATION_FAILED`. It re-checks the flag, source, onboarding and the batch's `draft` status and expiry.
   - With zero ready rows it returns `IMPORT_NOTHING_TO_IMPORT`.
   - Otherwise it sets `status = committing` and `commit_idempotency_key` in one conditional update, enqueues `import.commit` (job ID `import-commit-<batchId>`), and returns 202 with the batch.
2. Repeating the request with the same key on the same batch returns the current batch (202 or 200) without enqueuing twice. A different key on a non-draft batch returns `IMPORT_BATCH_STATE_CONFLICT`. The same key reused for a different batch in the org returns `IMPORT_IDEMPOTENCY_CONFLICT`.
3. **Through the ingestion command.** The commit job maps each ready row to `CanonicalOrderInput` with a `FileImportChannelAdapter` and calls `StandaloneOrderIngestionService.acceptMany(ctx, inputs, {channel: 'bulk_import', hold: {groupId: batchId}})`. The `order-imports` module never imports the ingestion repository, the envelope builder or the dispatcher.
   **One acceptance implementation.** The per-order body of `ManualOrderIngestionRepository.runAcceptance` (event insert or reload, ownership and fingerprint checks, order insert, link) is extracted to `acceptWithinTransaction(tx, input, {hold})`.
   - `accept()` for manual orders becomes one transaction around one call, with unchanged behavior and errors.
   - The new `acceptMany(inputs, {hold})` is one transaction around a chunk of calls.
   - `assertPersisted` is generalized to read back a list of order IDs.
   - Inside `acceptMany`, each row runs in its own savepoint (a nested `tx.transaction`), so one conflicting row rolls back only itself, not the chunk.
   - The only difference between the paths is the `hold` option, which sets `hold_state`, `hold_group_id` and `dispatch_required = false` instead of `true` and `NOW()`.
   - The job processes `ready` rows without an `order_id` in row-number order, in chunks of 200, one `acceptMany` per chunk. For each row:
   1. Build the bulk envelope with the shared `buildStandaloneOrderEnvelope` (US-04.6-01), with `externalOrderId` = `ref:<key>`, or `imp:<batchId>:<rowNumber>` when there is no reference, and `orderNumber` = the reference as written, or `IMP-<shortCode>-<rowNumber>`.
   2. Insert the `webhook_events` row with `platform = 'standalone'`, `idempotency_key = import:<batchId>:<rowNumber>`, `hold_state = 'held'`, `hold_group_id = batchId` and `dispatch_required = false`, using `onConflictDoNothing`.
   3. Insert the order using `onConflictDoNothing` on `(integration_id, external_order_id)`.
   4. Link the row's `order_id` and `webhook_event_id`, and set `outcome = 'imported'`.
4. **Commit-time race:** if the order insert conflicts because another batch or order already owns `ref:<key>`, the row becomes `duplicate` / `ALREADY_IMPORTED`, and the event inserted for it is deleted in the same transaction. No order or event is left orphaned.
5. **Resume after a crash:** a re-run skips rows that already have an `order_id`. It re-links rows whose event already exists (found by idempotency key) without creating anything new. BullMQ retries use the shared job options; a stalled job resumes from the next unlinked row.
6. After each chunk, the counts are recomputed from rows, and `progress = imported ÷ ready_at_commit` is visible via `GET /:id`. On completion the batch becomes `awaiting_start`, with `committed_at` and `start_deadline_at = committed_at + 72h`, and a persistence read-back asserts that every imported row's order exists (the same spirit as `assertPersisted`).
7. If a chunk fails 5 times the batch becomes `failed`. Rows already imported stay held and remain startable. The UI shows "Imported {n} of {m}. {m−n} could not be imported" and offers the error report, so the merchant can re-upload the remainder.
8. **Imported screen:** a success header "{n} orders imported", a reassurance line "Nothing has been sent to customers yet", counts (imported, need fixing, duplicates, excluded, duplicate at import time), the start deadline ("Start before {deadline} or these orders won't be confirmed"), and actions "Start WhatsApp confirmation" (US-04.6-07), "Review orders" (opens verifications filtered to this import) and "Download report".
9. Imported orders appear in the verifications list with the `awaiting_start` badge. Creating a manual order at the same time is unaffected and never waits behind the commit job.

## Edge cases

- Double-click on Import (one request is effectively a no-op).
- Two tabs committing with different keys (one wins; the other gets `IMPORT_BATCH_STATE_CONFLICT` and refreshes to the current state).
- The draft expires between review and commit (`IMPORT_BATCH_EXPIRED`).
- A concurrent batch commits overlapping references (the per-row conflict path).
- A manual order with the same order number created during the commit (it was L3 only at validation, so both orders exist; this is accepted and documented).
- A worker restart mid-chunk (transaction rollback, then re-run).
- The database is briefly unavailable (the job retries with backoff and the batch stays `committing`; the UI keeps polling).
- The flag is disabled after commit starts (the commit finishes; start is blocked).

## Implementation notes

- **Backend:**
  - There is **no** second ingestion repository. Refactor `ManualOrderIngestionRepository` as described in AC3. Optionally rename it to `StandaloneOrderIngestionRepository` with a re-export under the old name, so existing imports keep working.
  - The commit-time `ALREADY_IMPORTED` handling in AC4 is the existing "generated identity already exists" branch, returned as a typed per-row result instead of a thrown error when `hold` is set.
  - Queue `order-import` (new BullMQ queue, concurrency 2, and at most one commit job per batch through a deterministic job ID).
  - Never call `dispatchById` in this story.
- **Frontend:** An imported-state view in `/imports/[batchId]`, polling every 2 s while `committing`. Emit the `order.created` domain event on completion so verification queries refresh. Add an "Import" filter chip on verifications by `importBatchId` (query param).
- **Data:** No new tables. Rows gain `order_id` and `webhook_event_id`. `orders.raw_payload` carries `ingestionType = 'bulk_import'`, `importBatchId` and `importRowNumber`, and the orders table gets no new columns.
- **Operations:** Log chunk start and end with counts, and the per-batch commit duration.
