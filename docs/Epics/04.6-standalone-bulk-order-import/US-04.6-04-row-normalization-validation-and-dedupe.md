## User story and value

As a merchant, I want every row checked and explained before anything is imported, so that I import only orders Akeed can really confirm and never message a customer twice for the same order.

**Business value:** Wasted credits, duplicate WhatsApp messages and support tickets are prevented at the cheapest point, before any order exists.

## Scope

- A pure validation pipeline from a raw row, mapping and options to a normalized order, an outcome and issues.
- Dedupe levels L1–L3.
- Collapsing line-item rows.
- The date-range summary.
- The per-row include override for possible duplicates.

**Out of scope:** Inline cell editing in Akeed, address validation, and geocoding.

## Acceptance criteria

1. **Digits and text:**
   - All values are NFC-normalized.
   - Arabic-Indic (`٠-٩`) and Persian (`۰-۹`) digits are converted to ASCII. `٫` becomes the decimal point, and `٬` is treated as a thousands separator.
   - Zero-width and bidi control characters are removed. Whitespace is collapsed.
2. **Phone** (required):
   - Strip spaces, dashes, dots, parentheses and slashes.
   - If the value contains two or more candidate numbers (separated by `/`, `,`, `؛` or ` or `), the row gets `PHONE_MULTIPLE`.
   - Scientific notation (`2.01012E+11`) gives `PHONE_SCIENTIFIC_NOTATION`.
   - `00` is treated as `+`.
   - Parse with `PhoneService` using the import country unless the value starts with `+`. `PhoneService` gains one core `parse(raw, region)` returning a typed result. The existing `standardize()` and the new `standardizeMobile()` both delegate to it, so there is one libphonenumber code path. `standardize()` keeps its current behavior and exceptions for existing callers.
   - Only `MOBILE` or `FIXED_LINE_OR_MOBILE` number types are accepted. A valid landline gives `PHONE_NOT_MOBILE`, an invalid number gives `PHONE_INVALID`, and an empty value gives `PHONE_MISSING`.
   - For `EG`, a 10-digit national number starting with `1` (leading zero lost by Excel) is accepted.
   - The normalized value is E.164.
3. **Name** (required):
   - Empty gives `NAME_MISSING`.
   - Longer than the shared canonical limit (255, the same as `CreateManualOrderDto`) gives `NAME_TOO_LONG`.
   - No letter in any script (digits, symbols or emoji only) gives `NAME_NOT_TEXT`.
   - First and last name are joined when both are mapped.
4. **Amount** (required):
   - Strip currency words and symbols (`EGP`, `LE`, `L.E`, `ج.م`, `جنيه`, `SAR`, `ر.س`, `ريال`, `AED`, `د.إ`, `$`, `USD`).
   - With both `,` and `.` present, the last one is the decimal separator.
   - With only `,`: it is a thousands separator when followed by exactly 3 digits (`1,250`), a decimal separator when followed by 1–2 digits (`750,5`), and otherwise `AMOUNT_AMBIGUOUS`.
   - The cleaned decimal string is then checked by the **shared** amount rule, the same pattern `CreateManualOrderDto.totalPrice` uses: greater than 0 (`AMOUNT_NOT_POSITIVE`), at most 2 decimals (`AMOUNT_TOO_PRECISE`), and at most 10 integer digits (`AMOUNT_TOO_LARGE`).
   - Non-numeric values give `AMOUNT_INVALID`; empty gives `AMOUNT_MISSING`.
   - The result is stored as a decimal string with 2 places.
5. **Currency:**
   - Mapped values are upper-cased, and common symbols and words map to ISO codes (`ج.م`/`جنيه`/`LE` → `EGP`).
   - An empty value takes the import's `defaultCurrency`.
   - A value not in `ONBOARDING_SHIPPING_CURRENCIES` gives `CURRENCY_UNSUPPORTED`.
   - Mixed currencies in one file are allowed.
6. **Payment:** the import decides only the canonical payment method. **Eligibility is decided by the existing `OrderEligibilityService.evaluateOrderForVerification`** (Standalone strategy), exactly as for manual orders at retry and in the worker.
   - A value the merchant classified `cod` becomes `paymentMethod = 'cash_on_delivery'` (the manual form's constant), with the original kept in `normalized.paymentMethodOriginal`.
   - A value classified `not_cod` keeps its original text.
   - A blank or unmapped value becomes `''`.
   - The row's candidate `NormalizedOrder` goes through the eligibility service with the source integration.
   - An ineligible reason `non_cod_payment_method` gives `excluded` / `PAYMENT_NOT_COD`. `missing_payment_signal` gives `excluded` / `PAYMENT_UNKNOWN_EXCLUDED`. This inherits `assumeCodWhenPaymentMissing` with no re-implementation.
7. **Order date:**
   - Parse using ISO, the chosen `dateFormat`, Excel serials, or ISO timestamps with an offset. The result is interpreted as a date in the store timezone.
   - Unparseable gives `ORDER_DATE_INVALID`.
   - More than 1 day after today gives `ORDER_DATE_FUTURE` (invalid).
   - More than 7 days before today gives `excluded` / `ORDER_TOO_OLD`.
   - The batch stores `order_date_min` and `order_date_max` over the ready rows.
8. **Order reference:**
   - Trimmed; at most the shared order-number limit of 100 characters (`ORDER_REF_TOO_LONG`), the same as `CreateManualOrderDto.orderNumber`.
   - Normalized key: lowercase, leading `#` stripped, internal whitespace removed. `dedupe_key = ref:<key>`.
   - Without a reference, `dedupe_key` is NULL and identity is assigned at commit.
9. **In-file duplicates (L2):**
   - Rows sharing a reference key with the same normalized phone and amount (a line-item export) collapse into the lowest row number. The others become `duplicate` / `DUPLICATE_IN_FILE`, with `collapsed_into` set.
   - Rows sharing a key but differing in phone or amount are all `invalid` / `ORDER_REF_CONFLICT_IN_FILE`.
   - Reference-less rows identical in phone, name, amount and date also collapse as `DUPLICATE_IN_FILE`.
10. **Already imported (L1):** a ready row whose `ref:<key>` already exists as `orders.external_order_id` for the source becomes `duplicate` / `ALREADY_IMPORTED`, with the existing order ID in its issue params.
11. **Possible duplicate (L3):** a ready row matching an existing source order with the same E.164 phone and amount created within 7 days, or the same `order_number` (case-insensitive) within 30 days, becomes `excluded` / `POSSIBLE_DUPLICATE`, with the matched order's number and date. `PATCH /rows/:rowNumber {include: true}` flips it to `ready` (`include_override = true`). No other excluded, invalid or duplicate row can be included; attempting it returns `IMPORT_BATCH_STATE_CONFLICT`.
12. **Shared field rules:** every limit and pattern above that also exists in `CreateManualOrderDto` (phone length, name, order number, amount, currency list, payment method length) is defined once in `src/shared/commerce/canonical-order.rules.ts`. The DTO decorators are refactored to read those constants with unchanged messages and behavior. The import validator calls the same pure validators, and only the cell-text cleanup (digits, separators, currency words) is import-specific.
13. A row with several issues records all of them. The outcome precedence is invalid > duplicate > excluded > ready. Validation is deterministic: the same raw rows, mapping, options and database state give the same results. Counts are recomputed from rows after each run.
14. `GET /api/order-imports/:id/rows?outcome=&cursor=&limit≤100` returns `rowNumber`, the mapped raw values, normalized values, outcome and issues (codes plus params, localized on the client), ordered by row number.

## Edge cases

The data and duplicate lists in the [epic edge-case catalogue](README.md#edge-case-catalogue) are the acceptance fixture list for this story, especially:
- Excel-stripped leading zeros
- a Saudi number in an Egypt import
- `1.250,00`
- `٧٥٠٫٥٠`
- mixed `COD`/`Paid`
- a Shopify 3-row order
- the same reference with a different phone
- the same customer ordering twice the same day

## Implementation notes

- **Backend:**
  - `row-validator.ts` is a pure function with no I/O except the injected eligibility evaluator. Don't copy any rule from `orders.service.ts`, the DTO or the eligibility strategy; import them. The dedupe lookups (L1 and L3) are batched set queries per validation run: one query for all reference keys, and one for phone and amount pairs within 7 days.
  - Reuse `PhoneService` through the shared `parse` core. Reuse `isCashOnDeliveryPaymentSignal` for auto-classification, and `OrderEligibilityService` for the final decision.
- **Frontend:** An issue-code → message map in `orderImport.issues.*` (AR/EN) with ICU params, e.g. "Order #{orderNumber} from {date} has the same phone and amount".
- **Data:** `normalized` jsonb holds exactly the fields of the bulk envelope's `order` object.
- **Operations:** Validation metrics by issue code, with no values.

## Test requirements

*Deviations (approved during planning).*
- **One additive migration, although the story says "No migration".** `drizzle/0038_order_import_validation_version.sql` adds `order_import_batches.validation_version integer NULL`, the only place "`validationVersion` on the batch" could live. It is re-runnable (`ADD COLUMN IF NOT EXISTS`) and is applied twice by the order-imports contract suite.
- **A merchant's `not_cod` choice always excludes the row with `PAYMENT_NOT_COD`**, even when the shared COD matcher would read the text as COD (for example the merchant marks the literal "COD" as not COD). Every other row's ready/excluded decision is `OrderEligibilityService.evaluateOrderForVerification` with the session source; `assumeCodWhenPaymentMissing` is not re-implemented.
- **The COD method is stored as the manual form stores it.** `cash_on_delivery` passes through the DTO's own transform (`normalizeCanonicalPaymentMethod`), so `normalized.paymentMethod` is `cash on delivery`, byte-equal to a manual order's canonical order.
- **`RowValidationService.validateBatch(scope, batchId)` takes `{orgId, source}`**, not only the batch id. Every query stays org-scoped, and the timezone, `assumeCodWhenPaymentMissing` and integration come from the session source. `PUT /mapping` passes `@ImportSource()` through; the route was already `write`.

*Acceptance criteria.*
- AC1: `text.ts`.
- AC2: `phone.ts` plus `PhoneService.standardizeMobile`.
- AC3: `name.ts`.
- AC4: `amount.ts`.
- AC5: `currency.ts`. A currency written in the amount cell is used when the currency cell is blank.
- AC6: `payment.ts` plus the eligibility service.
- AC7: `date.ts` (store timezone via a cached `Intl.DateTimeFormat`) and the summary SQL.
- AC8: `reference.ts`.
- AC9: `applyInFileDedupe`.
  - A line-item row may leave phone, name and amount blank; the blanks agree with the group, and its `*_MISSING` issues are dropped when it collapses.
  - A reference with two present phones or amounts, or an unparseable one, makes every row in the group `ORDER_REF_CONFLICT_IN_FILE`.
- AC10: L1, one `external_order_id IN (…)` query for the source.
- AC11: L3.
  - One phone query (7 days, amount matched in memory) and one `lower(order_number)` query (30 days), with `POSSIBLE_DUPLICATE {orderNumber, date, match}`.
  - PATCH only for rows whose sole judged issues are `POSSIBLE_DUPLICATE`; anything else answers 409 `IMPORT_BATCH_STATE_CONFLICT`.
- AC12: the shared rules file and the DTO refactor.
- AC13: `outcomeOf`.
  - All issues are recorded.
  - Parser issues are carried across runs. `FIELD_TOO_LONG` on an unmapped column is stored as `informational` and does not change the outcome.
  - Counts are recomputed from rows.
- AC14: `GET :id/rows`.
  - `raw` holds the mapped fields only, keyed by field.
  - A bad query, cursor or row number answers `IMPORT_VALIDATION_FAILED`.
  - A missing row on PATCH answers `IMPORT_VALIDATION_FAILED` with `fieldErrors.rowNumber`; the contract has no row-not-found code.

*Known limitations.*
- The L3 windows (7 and 30 days) and the 7-day age window are the pilot ASSUMPTIONS named in this story.
- With `dateFormat: auto`, a value that its column cannot settle falls back to the column's detected order, else DMY. The mapping step already forces a choice for an ambiguous column.
- In a line-item group the lowest row is kept even if it is the one with blank cells.
- Validation metrics are logged per run as issue-code counts (`order-import-validate`). Dashboards come with US-04.6-09.
