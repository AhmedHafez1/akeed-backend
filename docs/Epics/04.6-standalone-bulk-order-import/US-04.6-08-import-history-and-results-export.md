## User story and value

As a merchant with no store integration, I want to see the confirmation outcome of my imported orders in the same Verifications list I already use for every other order, so that I don't have to learn a second screen or wait for a separate report to know what happened.

**Business value:** An imported order is still an Akeed order. Reusing Verifications is the entire feature — it gives the merchant a result they can act on today, without building and maintaining a second results UI before any real merchant has used bulk import.

## Scope

- A `?importBatchId=` filter on the existing Verifications page, with a dismissible "From import: {file}" chip — org-scoped, and already wired end-to-end (API query param, org-scoped query, frontend chip and link) by US-04.6-06. This story extends and verifies it; it does not rebuild it.
- Extending the same "view filtered orders" navigation to every batch state, not only the imported one: the `releasing`, `paused`, `stopped` and `completed` panels introduced by US-04.6-07 each get a "View orders" link into the filtered Verifications list, matching the link `ImportedView` already has from US-04.6-06.
- Confirming the existing Verifications table, statuses, lifecycle rendering, pagination, existing filters, and existing loading/empty/error states are used unchanged for imported orders — no second table.
- The "New import" action on the Verifications page header (added by US-04.6-05) remains the entry point into the import flow. No sidebar entry, no `/imports` history list.

**Out of scope (see [Deferred / Post-MVP](#deferred--post-mvp)):** `results.csv` / `errors.csv` exports, XLSX export, a `/imports` history page, a dedicated batch-detail results page, a new confirmation-results table or chart, a live import-specific dashboard.

## Acceptance criteria

1. `GET /api/verifications?importBatchId=<batchId>` continues to work exactly as delivered in US-04.6-06: org-scoped through `order_import_rows`, merged with real verifications in one cursor. A foreign or non-existent batch id yields zero rows (it is a filter parameter, not a resource lookup, so there is no 404 case to add here). No endpoint changes are required by this story; this criterion exists so the behavior stays covered by regression tests going forward.
2. The Verifications page shows the dismissible "From import: {file} ×" chip whenever `importBatchId` is present in the URL, exactly as delivered in US-04.6-06. Dismissing it clears the query param and returns to the unfiltered list without losing any other active filter.
3. Every batch-status view under `/imports/[batchId]` — `awaiting_start` (already linked by US-04.6-06's `ImportedView`), `releasing`, `paused`, `stopped` and `completed` (introduced by US-04.6-07) — shows a "View orders" action linking to `/verifications?importBatchId=<id>`, reusing the same href builder and translation key `ImportedView` already uses. No new component.
4. The Verifications table's columns, status badges, lifecycle rendering, pagination, existing filters (status, search, date) and existing order-details navigation are used unchanged for imported orders. Clicking into an order behaves exactly as it does for a manual order.
5. If a batch's filtered Verifications view currently has no rows (every row excluded or invalid, or none released yet), the page shows the existing Verifications empty state — not a new "no import results" screen.
6. This story adds no sidebar entry and no `/imports` list route. The "New import" entry point from US-04.6-05 remains how merchants start an import.

## Edge cases

- A batch with 0 rows currently visible in Verifications (all excluded/invalid, or none released yet) → the existing Verifications empty state.
- An `importBatchId` belonging to another organization → the org-scoped filter yields zero rows; another org's orders are never shown.
- An `importBatchId` that does not exist → zero rows, no error page.
- Dismissing the chip mid-session → returns to the full, unfiltered Verifications list without losing other active filters.
- A `releasing` batch: newly released orders appear in the filtered view as they're released, using the Verifications page's existing refresh behavior — no import-specific polling.

## Implementation notes

- **Backend:** None expected. The filter and its org-scoping already exist (`VerificationsRepository.findHeldByOrg` / `countHeldByOrg`, merged into `VerificationsService.listByOrg`, `?importBatchId=` on `GetVerificationsQueryDto` — all delivered by US-04.6-06). If a regression is found here, fix it in place rather than re-implementing it.
- **Frontend:** Add the "View orders" link to the `releasing`, `paused`, `stopped` and `completed` batch views next to the existing pattern from `ImportedView` (US-04.6-06). Reuse the same href builder and translation key; don't add a second one.
- **Data:** No new tables, no new columns.

## Test requirements

- A regression test that `?importBatchId=` still returns only the requesting org's rows and still merges held and real verifications correctly (already covered by US-04.6-06's suite — re-run and record it here rather than duplicating it).
- A frontend test/screenshot that every batch state (`awaiting_start`, `releasing`, `paused`, `stopped`, `completed`) renders a working "View orders" link.
- A frontend test that the empty state shown for a filtered, empty Verifications result is the existing Verifications empty state, not new markup.
- Satisfy the applicable [shared Definition of Done](../README.md); record test results during implementation, not when this backlog is authored.

## Migration and rollout

None. No new endpoints, tables or navigation entries are added.

## Deferred / Post-MVP

These were in scope in an earlier draft of this story and are explicitly deferred until real merchant usage of bulk import shows they're needed:

- `results.csv` and `errors.csv` streamed exports (formula-injection-safe escaping, UTF-8 BOM, CRLF, localized columns).
- XLSX export.
- A dedicated `/imports` history list page and its sidebar entry.
- A dedicated batch-detail results page (the stacked confirmation bar, the "mapping used" disclosure, per-batch download actions).
- A second confirmation-results table or a new charting system.
- A live, import-specific progress dashboard beyond the existing batch-status panels from US-04.6-06/07.
- The 5,000-row export performance requirement and the post-retention export fallback.
- Wiring the "Download rows to fix" (US-04.6-05) and "Download report" (US-04.6-06) actions that were stubbed disabled pending this story — they stay disabled until a future, explicitly-scoped export story exists.

If usage after MVP shows merchants genuinely need a downloadable file (for example, to share with a warehouse team that doesn't use Akeed), revisit that as a new, small story scoped to just that need — not a rebuild of the removed M9/M10 designs.
