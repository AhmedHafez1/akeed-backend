# US-04.6-01 — Add a source-neutral order hold and release primitive

- **Epic:** [E04.6 — Standalone Bulk Order Import (CSV / XLSX)](README.md)
- **Delivery rank:** 1 of 10
- **Priority:** P0
- **Horizon:** NEXT
- **Story type:** Technical enabler
- **Status:** Backlog
- **Dependencies:** [US-04-03](../04-standalone-manual-order-mvp/US-04-03-manual-order-verification-lifecycle.md)

## User story and value

As a Standalone merchant, I want imported orders to exist in Akeed without contacting any customer until I decide to start, so that uploading a file can never message customers by accident.

**Business value:** Import becomes a safe, reversible step. The confirmation engine stays source-agnostic because the hold lives on the durable ingestion event, not in a CSV-specific code path.

## Scope

- Hold state on `webhook_events`.
- Repository operations to create, release and withdraw held events.
- The dashboard lifecycle projection for held and withdrawn orders.
- Normalizer acceptance of the `bulk_import` envelope.
- An automated manual/bulk equivalence test.

**Out of scope:** File parsing, the import UI, pacing (US-04.6-07) and any change to Shopify ingestion.

## Acceptance criteria

1. `webhook_events` gains `hold_state` (`none` default, `held`, `released`, `withdrawn`), `hold_group_id` (nullable UUID, the import batch), `held_at`, `released_at` and `withdrawn_at`. Every existing row reads as `none`, and existing behavior is unchanged.
2. A held event is persisted with `dispatch_required = false` and `next_dispatch_at = NULL`. `recoverablePredicate` additionally requires `hold_state IN ('none','released')`, so neither `dispatchById` nor the reconciler can claim a held or withdrawn event, even if `dispatch_required` is set by mistake.
3. `releaseHeld(eventIds, dispatchAt)` updates only rows where `hold_state = 'held'`. It sets `released`, `dispatch_required = true`, `next_dispatch_at` and `released_at` atomically, and returns only the IDs it changed. Releasing twice is a no-op.
4. `withdrawHeld(groupId | eventIds)` updates only `held` rows to `withdrawn` with `status = 'skipped'` and `last_error = 'import_not_started'`. A withdrawn event can never be released afterwards.
5. The `retryGuardStatus` projection returns `awaiting_start` for `held` events and `not_started` for `withdrawn` events. Both are non-retryable. The dashboard badge, filter chips and translations (AR/EN) render them. The retry endpoint rejects them with `MANUAL_ORDER_RETRY_NOT_ALLOWED`.
6. `StandaloneManualOrderNormalizer` accepts any `ingestionType` in one shared constant, `STANDALONE_INGESTION_CHANNELS = ['manual','bulk_import']` (E05 appends `'api'`), with `schemaVersion 1` and the same required fields. For identical order data, the manual and bulk envelopes normalize to identical `NormalizedOrder` values, except `rawPayload`.
7. `VerificationHubService` and the send path contain no branch on `ingestionType`, `hold_group_id` or any import identifier. This is asserted by a test.
8. **Single envelope builder:** the inline canonical-order, fingerprint and `rawPayload` construction in `OrdersService.createManualOrder` moves to `src/shared/commerce/standalone-order-envelope.ts`, as `buildStandaloneOrderEnvelope({ingestionType, order, extras})` and `fingerprintCanonicalOrder(order)`. `createManualOrder` uses it. For the same input, the manual `rawPayload` and `submissionFingerprint` stay **byte-identical** to today, so existing idempotency replays still match. Bulk import (US-04.6-06) must use the same builder.
9. The normalizer's required-field list and the envelope builder read one shared definition of the canonical order fields, so the builder and the normalizer cannot drift.
10. **The Standalone ingestion command (adapter boundary):**
    - A `CanonicalOrderInput` type (`externalOrderId`, `orderNumber`, `customerPhone` (E.164), `customerName`, `totalPrice`, `currency`, `paymentMethod`, optional `extras`) and `StandaloneOrderIngestionService.acceptOne(ctx, input, {channel, idempotencyKey, hold?})` are introduced.
    - The service owns envelope building, fingerprinting, repository acceptance, the `hold` option and, when not held, the `dispatchById` call with the existing 503 semantics.
    - It also owns idempotency-key namespacing per channel (manual keys unchanged for backward compatibility; import `import:<batchId>:<row>`; E05 API `api:<key>`) and the shared order-reference normalizer (`ref:<normalized>`). This lets file import and the E05 API resolve the same merchant order to the same `externalOrderId`.
    - `OrdersService.createManualOrder` is reduced to a `ManualOrderChannelAdapter` (DTO → `CanonicalOrderInput`, manual external ID) plus `acceptOne`, with identical responses, codes and fingerprints.
    - Source resolution (US-04.6-02) and readiness (US-04.6-07) move into this service as they are extracted.
11. `ingestionType` is set by the service from `channel`. Channel adapters cannot write orders or events, dispatch or evaluate credits; a static test asserts that nothing outside `StandaloneOrderIngestionService` imports the ingestion repository or calls `dispatchById` for Standalone orders, except the retry endpoint and the release scheduler (US-04.6-07).

## Data contract

```text
webhook_events
  + hold_state      text NOT NULL DEFAULT 'none'  CHECK (hold_state IN ('none','held','released','withdrawn'))
  + hold_group_id   uuid NULL
  + held_at, released_at, withdrawn_at  timestamptz NULL
  + INDEX (hold_group_id, hold_state) WHERE hold_group_id IS NOT NULL
  + CHECK (hold_state <> 'held' OR dispatch_required = false)

bulk envelope (rawPayload)
  { ingestionType: 'bulk_import', schemaVersion: 1, submissionFingerprint,
    importBatchId, importRowNumber,
    order: { externalOrderId, orderNumber, customerPhone, customerName,
             totalPrice, currency, paymentMethod, paymentSignals, codStatus,
             orderDate?, city?, address?, notes? } }
```

## Edge cases

- A held event must not show as `accepted` or `processing`, which would imply a send is imminent.
- The reconciler must never pick up held rows after a restart, even with `WEBHOOK_RECONCILIATION_ENABLED=true`.
- A concurrent release and withdraw on the same event: exactly one wins, and the other reports zero rows changed.
- Existing manual orders created before the migration keep rendering exactly as before.

## Implementation notes

- **Backend:** Create `src/modules/order-ingestion/standalone-order-ingestion.service.ts` (the command), with channel adapters living with their controllers (`orders/manual-order.channel-adapter.ts`, later `order-imports/file-import.channel-adapter.ts`). Add the repository methods to `WebhookEventsRepository`. Extend the shared predicate once rather than filtering in callers. Keep the `retryGuardStatus` CASE as the single lifecycle source, adding branches before `webhookEvents.status = 'pending'`.
- **Frontend:** Extend the lifecycle union, `lifecycleToneClasses.ts` (neutral tone for `awaiting_start`, muted for `not_started`), the status filter options and the `dashboard` translations: "Awaiting start / بانتظار البدء" and "Not started / لم يبدأ".
- **Data:** Additive Drizzle migration with defaults, with no backfill beyond the default. The check constraint guards against a held event that is dispatchable.
- **Operations:** Log hold transitions with batch and event IDs only, never phone or name.

## Test requirements

- Repository tests: predicate exclusion, idempotent release, withdraw after release (no-op), and concurrent release against withdraw.
- Equivalence test: a manual envelope and a bulk envelope with the same order produce the same normalized order, the same verification creation and the same credit hold.
- Golden test: fingerprints and `rawPayload` from the extracted builder equal the pre-refactor values for recorded fixtures. Existing stored manual events still replay as duplicates, not conflicts.
- A projection test for all four hold states, plus a regression test that existing lifecycle outputs are unchanged.
- Satisfy the applicable [shared Definition of Done](../README.md); record test results during implementation, not when this backlog is authored.

## Migration and rollout

The migration is additive and safe before any UI ships. Rollback: leave the columns in place (unused). Rows with `hold_state = 'held'` must be withdrawn before the code that honors the predicate is reverted.
