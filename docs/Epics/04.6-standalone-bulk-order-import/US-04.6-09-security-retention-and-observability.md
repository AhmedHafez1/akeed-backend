# US-04.6-09 — Secure, retain and observe bulk import

- **Epic:** [E04.6 — Standalone Bulk Order Import (CSV / XLSX)](README.md)
- **Delivery rank:** 9 of 10
- **Priority:** P0

## User story and value

As an Akeed operator responsible for merchant and customer data, I want bulk import to be tenant-isolated, minimally retained, auditable and observable, so that a feature that handles thousands of customer phone numbers at once cannot leak, linger or fail silently.

**Business value:** Bulk personal data is the highest-impact data path in the product. This story makes it safe to launch and supportable afterwards.

## Scope

- Authorization and tenant checks across all endpoints.
- Upload hardening review.
- The retention and purge jobs.
- The audit trail.
- Log redaction.
- Metrics, alerts and the runbook.
- The feature-flag kill switch.
- Staff read-only visibility.

**Out of scope:** A general merchant audit-log UI, malware scanning of uploads (files are never stored or served back), and DLP tooling.

## Acceptance criteria

1. **Authorization:**
   - Every order-import endpoint resolves the org and source from the session.
   - A batch or row lookup always filters by `org_id`, and another org's ID returns 404 `IMPORT_BATCH_NOT_FOUND`, never 403.
   - Queries run under the same RLS policy as `orders`.
   - A test matrix covers owner, admin, viewer, another org's owner, an unauthenticated caller, a Shopify org and the flag turned off, for every endpoint.
2. **Upload hardening:**
   - Memory storage only; the file buffer is released after parsing.
   - No filesystem writes and no file name used as a path.
   - Limits enforced before parsing, and parser time capped at 20 s, which aborts with `IMPORT_FILE_UNREADABLE`.
   - The XLSX reader is configured to ignore external links, macros and embedded objects.
   - Cell values are stored as data and never interpreted.
   - The request body is excluded from error reporting and logging middleware.
3. **Retention:** a daily `import.purge` job:
   - Deletes `draft` batches past `expires_at` along with their rows, marking the batch `expired` and keeping a counts-only record.
   - For committed batches older than 90 days, sets `raw = NULL` and `normalized = NULL` on rows and keeps the outcome, issues, order ID and row number.
   - Deletes mapping profiles unused for 365 days.
   - Is idempotent and batched (1,000 rows per statement).
4. **Audit:** the batch permanently records `created_by`, `committed_at` with the commit actor, `attested_by`/`attested_at`/`attestation_version`, `started_at`, the stop actor and time, and resume and pause history (a jsonb `events` array of `{type, actorId?, reason?, at}`, append-only). These survive retention purges.
5. **Logging:**
   - Order-import code logs through `buildBackendLog` with the batch ID, org ID, counts, codes and durations only.
   - Phone numbers, names, addresses, amounts, file names and cell values are never logged. A unit test scans the log calls with a fixture file for PII leakage.
6. **Metrics and alerts:**
   - The metrics listed in the [epic README](README.md#metrics-and-release-gate) are emitted.
   - Alerts fire for: a release stalled 10 minutes outside quiet hours; a commit job stuck in `committing` for more than 15 minutes; an upload failure rate above 20% over 1 hour; and the purge job failing twice in a row.
7. **Kill switch:** setting `STANDALONE_BULK_IMPORT_ENABLED=false` hides navigation and blocks upload, mapping, commit, start and resume (`IMPORT_DISABLED`). Stop, exports and history keep working, and releasing batches finish. A documented emergency procedure pauses all releasing batches by SQL/admin action with reason `staff_paused`, which only staff can resume.
8. **Staff visibility:** the admin store view (`admin/stores/[integrationId]`) shows a read-only list of the org's import batches with status, counts, attestation and pause reason. No row data is shown. Access is audited in `admin_access_audit`.
9. **Runbook** at `docs/runbooks/bulk-order-import.md` covers:
   - diagnosing a stuck commit or release;
   - resuming or stopping on behalf of a merchant;
   - recovering from worker loss;
   - answering "did my customers get messaged?";
   - the purge schedule;
   - the kill switch.

## Edge cases

- Brute-force enumeration of batch IDs (UUIDs, 404, throttled).
- A viewer calling mutation endpoints.
- A session from a removed membership.
- An upload body containing a 5 MB single line.
- An XLSX with an external workbook link.
- A purge running during a results export (the export uses a snapshot or tolerates nulls).
- The flag being flipped repeatedly.
- A staff pause racing a merchant resume (the staff reason wins; the merchant sees "Paused by Akeed support").

## Implementation notes

- **Backend:**
  - A guard or decorator for flag, source and role shared by all order-import routes.
  - Purge and expire jobs on the `order-import` queue as repeatable jobs.
  - Metrics through the existing logging/metrics conventions.
- **Frontend:** A "Paused by Akeed support" state. The admin read-only panel.
- **Data:** Add the `events` jsonb to `order_import_batches`, plus an index for the purge scans on `(status, expires_at)` and `(committed_at)`.
- **Operations:** The runbook, alert configuration and a dashboard panel.

## Test requirements

- The authorization matrix; purge idempotency and the retention boundary; the log PII scan; the parser timeout; kill-switch behavior per endpoint; staff pause precedence.
- Satisfy the applicable [shared Definition of Done](../README.md); record test results during implementation, not when this backlog is authored.

## Migration and rollout

An additive migration for `events` and the indexes. Enable purge jobs before the flag is turned on for any pilot organization.
