## User story and value

As an Akeed operator responsible for merchant and customer data, I want bulk import to be tenant-isolated, safe to accept uploads for, free of customer PII in logs, and bounded in how long it retains raw imported data, so that a feature touching thousands of phone numbers at once can be exposed to real merchants without inventing a new incident.

**Business value:** This is the minimum bar to let real merchants use bulk import — not an operations platform. Anything beyond stopping tenant leaks, unsafe uploads, PII logging and indefinite data retention is deferred until real usage justifies building it.

## Scope

- A tenant-isolation test matrix across every order-import endpoint.
- A hardening review — plus tests for any gap found — of upload handling already built by US-04.6-02.
- A focused PII-log test across the full upload → commit → start → release flow.
- One daily retention/purge job for committed batches' raw row data.
- Confirming the `STANDALONE_BULK_IMPORT_ENABLED` kill switch covers every mutation endpoint and hides every entry point.

**Out of scope (see [Deferred / Post-MVP](#deferred--post-mvp)):** a metrics dashboard, alerting infrastructure, a staff read-only import UI, a staff pause/resume workflow, an admin import-access audit system, a detailed runbook, malware scanning, DLP, mapping-profile cleanup, production SLA/performance monitoring.

## Acceptance criteria

1. **Tenant isolation — MUST HAVE.**
   - Every order-import endpoint resolves `org_id` and the writable source from the authenticated session, reusing `StandaloneSourceResolver` — no new resolver or authorization framework.
   - A batch or row lookup filters by `org_id`; another organization's batch id returns 404 `IMPORT_BATCH_NOT_FOUND`, never 403, matching the existing pattern for orders.
   - Queries run under the same RLS policy as `orders` (`org_id = get_user_org_id()`), reused as-is.
   - A test matrix covers {owner, admin, viewer, another org's owner, an unauthenticated caller, a Shopify org, the flag off} × every order-import endpoint (upload, mapping, commit, start-quote, start, stop, resume, discard, the batch/rows reads, and the Verifications `importBatchId` filter). Mutation endpoints reject viewers with the existing role-check pattern.
2. **Basic upload hardening — MUST HAVE.**
   - Confirm — and close any gap found in — what US-04.6-02 already built: memory-only storage with the buffer released after parsing, no filesystem writes, the file name never used as a path, limits enforced before parsing.
   - The parser time cap (20 s) actually aborts pathological input with `IMPORT_FILE_UNREADABLE`; add the test if US-04.6-02 didn't include one.
   - The XLSX reader ignores external workbook links, macros (`vbaProject.bin`) and embedded objects — confirmed with a fixture containing an external link, not only a macro fixture.
   - Cell values are only ever read as data, never evaluated as formulas — already the parser's design; add a regression test if one is missing.
   - The raw request body and uploaded file are excluded from error-reporting and logging middleware.
   - No malware scanning, DLP or antivirus infrastructure is added. Uploaded files are never stored or served back — that remains the mitigation.
3. **PII-safe logging — MUST HAVE.**
   - Order-import code logs only through `buildBackendLog` with batch ID, org ID, status, counts, error codes and durations.
   - Phone numbers, customer names, addresses, raw cell values, raw uploaded files and full order payloads are never logged — building on US-04.6-02's existing `REDACTED_KEYS` additions (`filename`, `file_name`, `originalname`, `cells`, `raw`).
   - One new focused test runs upload → commit → start → release with a fixture containing unique marker phone numbers, names and addresses, captures all logger output, and asserts none of the markers (or the file name) appear anywhere in it. This is the one new PII test this story requires; it covers the commit/start/release stages that US-04.6-02's existing log test didn't reach.
4. **Basic retention — KEEP IT SIMPLE.**
   - Reuse what already exists: the 24-hour draft expiry and row purge (US-04.6-02) and the 72-hour start-window expiry (US-04.6-07). Neither changes.
   - Add exactly one new job: a daily `import.purge` job that, for committed batches older than 90 days, sets `raw = NULL` and `normalized = NULL` on their rows while keeping outcome, issues, order ID and row number. Batched (1,000 rows per statement) and idempotent (safe to re-run).
   - No retention reporting, no second retention subsystem, and no mapping-profile cleanup in this story.
5. **Feature flag / kill switch — KEEP.**
   - `STANDALONE_BULK_IMPORT_ENABLED=false` hides every import entry point (the "New import" action, the batch-status routes) and blocks upload, mapping, commit, start and resume with `IMPORT_DISABLED`.
   - Stop, and the existing Verifications filter for already-imported orders, keep working.
   - Releasing batches continue exactly per the existing US-04.6-07 behavior; this story adds no new pause mechanism.
   - A test confirms the flag is checked on every mutation endpoint (not only the upload guard) and that flipping it repeatedly leaves no batch in an inconsistent state.

## Edge cases

- Brute-force enumeration of batch IDs (UUIDs; 404; the existing per-user upload throttle from US-04.6-02 is the only rate limiting required here).
- A viewer calling any mutation endpoint.
- A session from a since-removed membership.
- An upload body containing a single 5 MB line with no delimiter — must not hang the parser past the 20 s cap.
- An XLSX with an external workbook link.
- The flag being flipped on and off repeatedly mid-batch.
- The daily purge job running twice in a row on the same day (idempotent, no double-null errors).

## Implementation notes

- **Backend:**
  - No new authorization framework — reuse `StandaloneSourceResolver` and the existing RLS pattern.
  - The purge job runs on the existing `order-import` BullMQ queue as a repeatable job, alongside `import.expire` (US-04.6-07).
  - Extend `REDACTED_KEYS` only if the PII-log test finds a gap; don't pre-emptively add fields that aren't logged.
- **Frontend:** No new UI. The existing "disabled by flag" and auto-pause states already built by US-04.6-07 are reused as-is.
- **Data:** No new columns. Add an index only if the 90-day purge query genuinely needs one (`committed_at` on the batch) — nothing else.

## Test requirements

- The authorization matrix described in AC1.
- The upload-hardening gap tests described in AC2 (parser timeout, external-link XLSX).
- The PII-log scan described in AC3.
- Purge-job idempotency and the 90-day boundary (day 89 vs. day 91).
- Kill-switch coverage per mutation endpoint.
- Satisfy the applicable [shared Definition of Done](../README.md); record test results during implementation, not when this backlog is authored.

## Migration and rollout

An additive index on the batch's `committed_at` (or on `order_import_rows` if the purge scan needs it there instead) only if the purge query requires one; otherwise none. Enable the purge job before the flag is turned on for any pilot organization.

## Deferred / Post-MVP

These were in scope in an earlier draft of this story and are explicitly deferred until bulk import has real usage to observe:

- A metrics dashboard and the underlying metrics architecture (`order_import.upload/validate/commit/release` counters, the funnel view).
- Alerts: a 10-minute release-stall alert, a commit-stuck alert, an upload-failure-rate alert, a purge-failure alert, and the alerting infrastructure behind them.
- A full operational dashboard, or a staff-facing import dashboard.
- A staff read-only batch UI on the admin store page, and the staff pause/resume workflow (with its history and precedence rules).
- An admin import-access audit system beyond the existing `admin_access_audit` table (unused by this story — there's no staff feature yet to audit).
- A detailed runbook (`docs/runbooks/bulk-order-import.md`) — write it once there's an actual incident shape to document, or earlier if US-04.6-10's pilot needs it sooner.
- 365-day mapping-profile cleanup (not required by any existing infrastructure today).
- Enterprise DLP or malware-scanning infrastructure.
- Extensive operational edge-case suites and production SLA/performance monitoring.

If the pilot in US-04.6-10 surfaces an operational gap (a stuck job nobody notices, a support request nobody can answer), address it as a small, targeted follow-up rather than building the full list above speculatively.
