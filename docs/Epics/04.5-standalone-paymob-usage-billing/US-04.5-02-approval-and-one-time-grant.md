## User story and value

As an approved Standalone merchant, I want my account activated with 30 free credits once, so that I can test real order verification before making a purchase.

**Business value:** Akeed controls launch access and gives every approved organization the same auditable trial allowance.

## Scope

Pending account provisioning, staff eligibility preview/apply, serializable activation, exactly-once free grant, onboarding/send gating, migration-cohort handling and complete staff audit.

**Out of scope:** Paymob checkout, recurring grants, automatic migration approval, converting old monthly usage, or changing Shopify onboarding/free-plan claims.

## Acceptance criteria

1. New Standalone provisioning creates/reuses an inactive `pending_approval` credit account and does not write Starter/not-required entitlement as paid-access authority.
2. Standalone onboarding completion and all new billable sends are blocked with `STANDALONE_APPROVAL_REQUIRED` until staff approval commits; read-only order/history access remains available.
3. Existing Standalone organizations appear in a staff preview queue with deterministic `eligible`, `already_approved`, `skipped` or `ambiguous` reasons. Shopify/native-source conflicts are never converted.
4. Staff apply requires production AAL2, the existing admin feature guard, a non-empty audit reason and a preview whose fingerprint still matches current organization/source/membership/account state.
5. Approval locks the organization/account and, in one serializable transaction, activates the account, inserts `free_grant +30` with key `standalone-free-grant:<orgId>:v1`, updates the projection and records actor/reason/time/request/before/after audit data.
6. Concurrent, repeated, timed-out or replayed approval produces one active account and one 30-credit ledger entry. A repeated identical request returns the existing outcome without another grant.
7. Existing organization membership, source identity, onboarding settings, orders, verifications, dispatches and monthly usage history are preserved. Old usage is not subtracted from or converted into the launch grant.
8. Approval can be run in bounded batches; one failed/changed organization does not corrupt successful rows and is reported with a safe reconciliation reason.
9. Shopify provisioning, Starter claim rules, billing callbacks and subscription fields are unchanged.

## Interfaces

Add an admin surface under `/api/admin/standalone-billing` using the existing staff auth/audit conventions:

- `GET /accounts?approval=&cursor=&limit=` returns safe preview/list fields.
- `POST /approvals/preview` accepts bounded organization IDs and returns a stored preview ID, fingerprints and per-row decisions.
- `POST /approvals/apply` accepts the preview ID plus required reason and returns per-row idempotent outcomes.

No merchant endpoint can self-approve or request the free grant. `GET /api/billing/credits` may expose pending/active status and grant-present state once its read API is introduced, but this story does not need the purchase endpoints.

## Implementation notes

- **Backend:** Replace the Standalone pilot’s plan grant with credit approval semantics or introduce the new controller while reusing its preview/fingerprint/serializable retry patterns. Avoid two staff paths that can grant independently.
- **Frontend:** Adapt the existing localized Standalone pilot admin page to the new status vocabulary; show reason, preview drift and per-row results. Merchant onboarding shows a localized waiting-for-approval state.
- **Data:** Free-grant uniqueness is database-enforced. Approval metadata on the account is descriptive; the immutable ledger key is the exactly-once authority.
- **Security:** Organization IDs are staff selection inputs only after admin authorization; every apply reloads and locks current state. Merchant identity still comes from dual auth.
- **Operations:** Keep apply behind a separate Standalone billing activation flag. Preview remains available while apply is disabled.

## Test requirements

- New and existing Standalone organization provisioning; Shopify exclusion; ambiguous source/membership rows.
- Owner/admin/viewer cannot self-approve; valid staff AAL2 succeeds; missing/invalid production AAL2 and disabled flag fail.
- Concurrent approval, duplicate apply, lost response/replay, preview drift, batch partial failure and serializable retry.
- Exactly one `free_grant +30`; account/ledger/audit before/after values reconcile.
- E03 onboarding/provisioning and E04 merchant workflow regressions, plus complete Shopify billing regression.

## Migration and rollout

Deploy behind disabled apply, populate pending rows, inspect the preview report, then approve an allowlisted cohort in small batches. Disable further apply on anomaly; never delete a committed grant or reset merchant history as rollback.
