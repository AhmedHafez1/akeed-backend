## User story and value

As an organization owner or admin, I want to pay for a chosen credit quantity by card or Vodafone Cash, so that verified payment adds credits without staff intervention or browser-side trust.

**Business value:** Akeed can collect prepaid EGP revenue safely and grant exactly what was purchased.

## Scope

Merchant purchase APIs, immutable server pricing, Paymob Create Intention adapter, Unified Hosted Checkout, processed callback HMAC, canonical payment state machine, purchase grants, inquiry recovery, refund/dispute ingestion boundaries and sanitized event persistence.

**Out of scope:** Direct Vodafone Cash integration, recurring subscriptions, saved cards/tokens, self-service refunds, arbitrary partial-refund automation, invoices or tax-policy decisions.

## Acceptance criteria

1. `POST /api/billing/purchases` requires an authenticated active Standalone owner/admin and `Idempotency-Key`; viewers, Shopify mode, pending/suspended accounts and cross-tenant access are denied.
2. The body accepts only integer `quantity`. Backend validates 100–5,000 in step 50, fixes unit price to 200 minor units and currency to `EGP`, computes total with checked integer arithmetic, derives organization/actor and ignores/rejects every browser-supplied price/status/provider field.
3. The backend persists one local `pending` purchase with an opaque unique internal reference and request hash before the network call. Same key/same quantity returns it; same key/different quantity returns `409`; no timeout creates a second Paymob intention for that key.
4. `PaymobPaymentsAdapter` alone sends Create Intention using `Token <secret>`, trusted amount/currency, card and wallet integration IDs, internal `special_reference`, configured expiration, sanitized billing data, item total, processed callback and return URL.
5. The response validates intention/order/client-secret/reference fields, persists safe provider identifiers and returns the Unified Hosted Checkout URL built from configured public key and returned client secret. The secret/URL is never logged or exposed to viewers/admin list APIs after its required short-lived use.
6. Card and Vodafone Cash are selected inside Paymob Unified Checkout. Akeed stores no PAN, CVV, wallet credential, reusable token or raw sensitive provider payload.
7. `POST /api/webhooks/payments/paymob` rejects missing/malformed/invalid HMAC and unsupported event types without changing purchase or credits. SHA-512 input uses Paymob’s exact documented field order and normalized values; comparison is timing safe on equal-length buffers.
8. After HMAC validation, callback processing matches internal reference plus stored amount, currency, integration ID, Paymob order/intention/transaction ownership and test/live mode. Any mismatch is sanitized/quarantined for reconciliation and grants nothing.
9. Verified `success=true` and `pending=false` atomically persists the event, promotes allowed prior states to `successful`, posts one `purchase +quantity` ledger entry and updates the account projection. Callback replay or a lost response cannot grant twice.
10. Canonical states follow the epic precedence: definitive decline/cancel, inquiry-confirmed expiry, delayed success promotion, no downgrade from success/refund, full verified refund to `refunded`, separate dispute status and no browser-triggered transition.
11. Exact full or original-price whole-credit refund reverses affected credits once. Non-exact partial refund records minor amount and requires reconciliation. Chargeback open/lost reverses once; won reinstates once. Debt is permitted and immediately blocks new holds.
12. Create timeout/5xx, missing callback, database rollback, delayed/out-of-order callback, expiry and replay recover through inquiry/event/ledger idempotency without duplicate intentions or grants.
13. Read APIs return canonical, organization-scoped, `private, no-store` credit summary, paginated ledger, purchase list and purchase detail; response DTOs contain trusted price/range/permissions and no secrets.

## Public API contract

- `GET /api/billing/credits`: status, posted/held/available, debt, free-grant state, threshold, server price/range/step and `canPurchase`.
- `GET /api/billing/credits/ledger?cursor=&limit=&type=`: opaque cursor pagination over immutable entries.
- `GET /api/billing/purchases?cursor=&limit=`: safe purchase history.
- `GET /api/billing/purchases/:purchaseRef`: canonical state for polling; reference must belong to the authenticated org.
- `POST /api/billing/purchases`: `{ quantity }`, `Idempotency-Key`; returns reference/state/trusted amounts/currency/checkout URL/expiry.
- `POST /api/webhooks/payments/paymob`: processed callback only; browser response callback is never sent here as authority.

## Callback HMAC contract

Concatenate normalized values in Paymob’s documented order:

`amount_cents`, `created_at`, `currency`, `error_occured`, `has_parent_transaction`, `obj.id`, `integration_id`, `is_3d_secure`, `is_auth`, `is_capture`, `is_refunded`, `is_standalone_payment`, `is_voided`, `order.id`, `owner`, `pending`, `source_data.pan`, `source_data.sub_type`, `source_data.type`, `success`.

The implementation must use fixtures copied from the enabled Paymob test account because absent/null and boolean serialization are provider contract details. Never sort arbitrary JSON keys or sign the raw body as a substitute for Paymob’s specified concatenation.

## Implementation notes

- **Backend:** Register the adapter behind `PaymentsPort`; use bounded timeouts/retries with jitter only where repeat safety is proven. Callback transition, event, ledger and projection are one database transaction.
- **Frontend:** This story may expose typed API functions and the minimal return route needed for contract tests; full merchant presentation belongs to US-04.5-05.
- **Data:** Store provider identifiers as strings, money in minor units and only sanitized error/reconciliation metadata. Event fingerprint includes provider action/transaction identity and status-relevant facts.
- **Security:** Secrets are server-only. Validate public HTTPS in live mode; reject localhost/test integration IDs in live configuration. Throttle callbacks without preventing legitimate provider retries.
- **Operations:** Inquiry handles stale/anomalous purchases. Staff may trigger inquiry but cannot manually mark an unmatched/unverified payment successful.

## Test requirements

- Quantity bounds/step/integer overflow, roles, mode, tenant isolation, server price and idempotency request hash.
- Adapter request/response contracts, 4xx, 5xx, timeout/lost response and secret-safe logging.
- HMAC valid/invalid/missing/malformed, nested path, boolean/null/string normalization and timing-safe comparison.
- Callback success, decline, cancel, duplicate, replay, delayed, out-of-order, mismatch/quarantine, refund, partial refund, chargeback and success-after-local-failure.
- Inject database failure after verified success; retry grants exactly once. Commit-success/lost-response replay returns 2xx without another grant.
- Missing callback/expiry inquiry and no-success confirmation before `expired`.
- Shopify services are never called by Standalone purchase and all Shopify billing regressions pass.

## Migration and rollout

Use Paymob test credentials and disabled production flag first. Configure processed callback on both card and wallet integration records; include per-intention `notification_url` where Paymob supports it (official Create Intention documentation currently states card-only). Do not enable wallet traffic until its actual callback behavior is captured in sandbox.
