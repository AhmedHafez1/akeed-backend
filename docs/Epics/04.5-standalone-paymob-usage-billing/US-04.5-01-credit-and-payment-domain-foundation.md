## User story and value

As an Akeed finance and support operator, I want payment and credit facts stored in separate, immutable, tenant-safe records, so that a merchant balance can be explained and repaired without changing Shopify billing data.

**Business value:** Every future grant, purchase, consumption and reversal has a trustworthy accounting foundation.

## Scope

Add the provider-neutral payment-purchase, credit-account, credit-reservation, credit-ledger and sanitized provider-event schema; projection invariants; data access boundaries; dispatch generation; configuration contract; and repository/domain ports needed by later stories.

**Out of scope:** Merchant approval, Paymob network calls, changing verification consumption, billing UI, live backfill activation or any credit grant.

## Acceptance criteria

1. An additive migration after `0031` creates `credit_accounts`, `credit_reservations`, `credit_ledger_entries`, `payment_purchases` and `payment_provider_events` without repurposing Shopify subscription columns or `integration_monthly_usage`.
2. Money is integer minor units, credit quantities are integers, ledger quantities are signed/nonzero, held credits cannot be negative, and every organization-owned relationship has a composite tenant foreign key or an equivalently enforced tenant invariant.
3. Unique constraints cover free-grant source, merchant purchase idempotency, purchase ledger source, provider intention/order/transaction IDs, callback fingerprint, reservation/billable identity, consumption/reversal source and staff-adjustment idempotency.
4. Ledger rows are immutable at the database boundary. Authenticated organization members can read only safe organization-scoped data and cannot perform direct DML; only the backend service role writes.
5. `credit_accounts.posted_balance` and `held_credits` are projections guarded by row locks/versioning. A documented invariant checker can compare ledger sum, held reservations and projection before later mutation code uses them.
6. Existing dispatches are generation 1. Dispatch identity can include a later generation without allowing two active generations or inventing retries for ambiguous outcomes.
7. Existing Standalone organizations are represented as pending approval only; no monthly usage is converted, no grant is posted and no paid balance is inferred.
8. Provider-neutral interfaces define checkout/inquiry and hold/consume/release/reverse/grant/adjust operations without importing Paymob into orders, verification or messaging.
9. Billing configuration parses the approved defaults but remains disabled by default. Enabling it with missing, placeholder, internally inconsistent or unsafe live callback configuration fails startup.
10. Applying the migration twice is safe where the project’s migration discipline requires replay tolerance, and rollback/forward recovery preserves all ledger and purchase history.

## Data contract

- `credit_accounts`: one row per organization; `pending_approval | active | suspended`, posted balance, held count, approval metadata, version and timestamps. Debt is a negative posted balance, not a separately mutable source of truth.
- `credit_reservations`: org/dispatch/kind/generation/quantity, unique billable key and `held | consumed | released` lifecycle with resolution metadata.
- `credit_ledger_entries`: immutable type, signed quantity, idempotency key, org plus optional reservation/dispatch/purchase source, actor/reason, before/after projection and timestamp.
- `payment_purchases`: internal reference, org/provider, request key/hash, immutable quantity/unit/total/currency, canonical payment/dispute state, provider identifiers, checkout expiry, refund fields and sanitized reconciliation metadata.
- `payment_provider_events`: provider identifiers, canonical fingerprint, payload hash, verified/result/error/retry metadata and timestamps; no raw card, wallet, token, email, phone or billing payload.

Ledger types are exactly `free_grant | purchase | consumption | failure_reversal | refund_reversal | chargeback_reversal | chargeback_reinstatement | staff_adjustment`. Purchase states are exactly `pending | successful | failed | canceled | expired | refunded`; disputes are `none | open | lost | won`.

## Implementation notes

- **Backend:** Add `PaymentsPort`, `CreditAccountingPort` and `UsageAccountingRouter` contracts. Keep controllers absent in this story. Expose transaction-aware repository operations so later dispatch and callback writes can share one database transaction.
- **Frontend:** No UI or API call changes. Add shared response types only if generated/contract types require the schema boundary, with no user-visible behavior.
- **Data:** Use an additive `0032` migration with preflight counts. Add safe indexes for account status, org/time histories, held reservations, pending/reconciliation purchases and provider events.
- **Security:** RLS read policies derive `get_user_org_id()`; revoke authenticated insert/update/delete. Do not expose provider checkout secrets through direct table read policies.
- **Operations:** Feature disabled. Record preflight totals for Standalone sources, accounts to insert, legacy dispatches and any identity anomalies before applying.

## Test requirements

- Disposable PostgreSQL migration, second-apply/idempotency check, forward recovery and schema constraint tests.
- Cross-tenant composite-FK and RLS tests under authenticated and service-role contexts.
- Ledger update/delete denial, duplicate idempotency keys, invalid quantities/money/statuses and projection invariant tests.
- Dispatch generation contract: generation 1 backfill, unique active billable identity and no retry after ambiguous state.
- Environment validation for disabled, valid test, invalid test and unsafe/placeholder live configurations.
- Current E04 migration contracts and Shopify entitlement contracts remain green.

## Migration and rollout

Deploy schema and code contracts with `STANDALONE_CREDIT_BILLING_ENABLED=false`. Backfill only pending account rows for organizations with a Standalone source. Do not null or reinterpret Standalone plan fields until the approval/usage-router stories are deployable together. Rollback disables readers/writers and leaves additive tables intact.
