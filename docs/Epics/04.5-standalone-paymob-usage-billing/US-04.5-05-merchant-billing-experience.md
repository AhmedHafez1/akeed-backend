## User story and value

As a Standalone merchant, I want to understand my credits, buy more and see what changed my balance, so that verification does not stop unexpectedly and payment status is never ambiguous.

**Business value:** Merchants can self-serve prepaid billing and recover from low balance or payment interruption without losing access to operational history.

## Scope

Standalone billing route/navigation, balance and debt presentation, quantity/price checkout flow, return-state polling, purchase and ledger histories, low/zero balance action handling, role differences, accessibility and Arabic/English localization.

**Out of scope:** Shopify billing redesign, staff adjustment controls, merchant refunds, coupons/tiered price, saved methods or embedded card fields.

## Acceptance criteria

1. Standalone navigation/settings links to `/[locale]/billing`; embedded Shopify navigation and billing tabs remain unchanged and do not expose Paymob credit controls.
2. Every organization member can see account status, posted/held/available credits, debt, launch-grant state, low-balance threshold, unit price, permitted quantity rules, purchase history and credit ledger history.
3. The page distinguishes `pending_approval`, `active`, `suspended`, low balance, zero and debt with actionable localized copy. Existing orders/verifications remain navigable in all states.
4. Owner/admin can choose only 100–5,000 credits in steps of 50. The UI previews `quantity × EGP 2.00`, labels card and Vodafone Cash as Paymob checkout methods and submits only quantity plus an idempotency key.
5. Viewer sees the same billing information but no enabled checkout action and a localized read-only explanation. Backend authorization remains authoritative if UI controls are bypassed.
6. Checkout response replaces the client preview with trusted quantity/unit/total/currency before redirect. The UI does not construct provider URLs or trust a browser-provided amount/status.
7. The Paymob return page ignores callback query values for activation, reads `GET /api/billing/purchases/:purchaseRef`, briefly polls pending state and offers safe refresh/retry navigation without creating a duplicate purchase.
8. Pending, successful, failed, canceled, expired, refunded, dispute/chargeback and reconciliation-required states have distinct accessible Arabic and English content. Success is shown only after the Akeed API reports canonical success.
9. Ledger rows show source/type, signed quantity, date and safe reference/actor/reason where appropriate. Purchase rows show reference, quantity, trusted total/currency, state, created/updated timestamps and refund/dispute visibility.
10. At 10 or fewer available credits, a warning encourages purchase. At zero/debt, manual create, test send and retry controls show the correct credit error and billing link while order/history screens remain usable.
11. Copy explicitly states that each Meta-accepted initial or follow-up message costs one credit, confirmed failures restore it, and paid credits do not expire.
12. Loading, empty, stale-poll, API error, disabled checkout, keyboard focus, responsive layout and RTL/LTR behavior are verified without exposing secrets or sensitive payment data.

## Page behavior

- Balance cards display available as the primary spendable value; held and posted explain reconciliation without presenting held as spendable.
- Debt displays the absolute EGP-independent credit amount and explains that the next purchase first clears debt.
- Quantity defaults to the approved minimum but is editable only through a step-safe number control; invalid direct input is corrected/explained before submit.
- A new idempotency key represents one deliberate checkout attempt and remains stable across network retry. A user choosing “start a new purchase” intentionally creates a new key.
- Redirect copy names Paymob and indicates that payment details are entered on Paymob’s hosted page.
- Return polling is bounded; background endless polling is excluded. A stale pending payment moves to a reconciliation message, not a guessed failure.

## Implementation notes

- **Backend:** Finalize read DTOs and cache headers. Never include checkout secret, event payload/hash, internal reconciliation metadata or cross-tenant identifiers.
- **Frontend:** Create `features/billing` with domain types, API wrapper, coordinator hook and Standalone skin. Use `fetchWithAuth`, shared error parsing, existing UI primitives and locale helpers.
- **Data:** Use opaque cursors; append results without client-side recomputation of balances. Ledger is the history, account is the projection.
- **Localization:** Add matching `en.json`/`ar.json` keys for all statuses, roles, warnings, amounts, refund/dispute, reconciliation and action errors. Format EGP and dates with locale APIs; keep identifiers LTR-safe within RTL.
- **Operations:** Support copy points to the staff reconciliation path for stale payment without promising immediate manual credit.

## Test requirements

- Owner/admin/viewer rendering and direct API denial; pending/active/suspended/low/zero/debt variants.
- Valid and invalid quantity, trusted server total replacement, stable idempotency retry and new-attempt key.
- Return page with pending→successful, failure, cancel, expiry, refund, chargeback, reconciliation and polling timeout.
- Verify redirect query cannot change displayed canonical success or balance.
- Ledger/purchase pagination, loading/empty/error/retry and no secret fields.
- English/Arabic, LTR/RTL, keyboard, screen-size and focus-return checks.
- Manual-order/test/retry zero-credit UX while list/detail/history remains accessible.
- Frontend typecheck, lint, isolated production build and current embedded Shopify screen snapshots/smoke checks.

## Migration and rollout

Hide the navigation/page when the feature is disabled except for explicitly allowlisted test accounts. Enable after API and callback sandbox evidence exists. Rollback hides purchase actions but keeps read-only billing/history and operational pages available.
