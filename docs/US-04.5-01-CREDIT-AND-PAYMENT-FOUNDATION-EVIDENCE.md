## Storage and access guarantees

- All money and quantities use PostgreSQL integers. Purchase totals use a bigint intermediate for multiplication; invalid totals, nonpositive purchase/reservation quantities, negative holds, zero ledger quantities, wrong ledger signs, and inconsistent before/after balances are rejected. Posted balances may be negative.
- Organization-owned references use tenant-safe foreign keys. Reservation references additionally match dispatch verification, kind, and generation. Reversal sources must match their original organization's purchase/reservation and the expected ledger type.
- Independent source indexes prevent repeated free grants, purchase postings, consumption, failure reversals, refund/dispute operations, and dispute reinstatement. Organization-scoped request keys cover purchases and ledger operations, including staff adjustments. Provider identifiers and event fingerprints are provider-scoped unique values.
- Ledger update/delete/truncate is denied by triggers, including owner-issued ordinary DML. Purchase deletion/truncation and changes to original economic terms or already-bound provider identifiers are denied. These protections do not purport to prevent a database owner from deliberately dropping tables or disabling triggers.
- Authenticated users receive only column-level SELECT grants on safe account, reservation, ledger, and purchase fields, with `org_id = get_user_org_id()` RLS. They receive no direct DML or provider-event access. Approval reasons/actors, idempotency hashes, reconciliation internals, and provider identifiers are excluded from those grants. Backend service-role writes are explicitly granted; ledger updates remain denied.
- Provider events store identifiers, hashes, verification/result/error codes, and retry timestamps/counts. There is no raw payload, checkout URL/client secret, card, wallet, token, email, phone, or billing-detail column. Reconciliation metadata uses structured columns rather than arbitrary JSON.
- Financial foreign keys do not cascade away history. Rollback is application-only and retains the added tables.

## Transaction and generation contract for subsequent stories

Repository mutation methods require `CreditTransaction`, derived from the existing Drizzle transaction type. They do not open independent transactions or make provider calls.

For a later credit mutation, the orchestrating service must:

1. Begin one database transaction and call `CreditAccountingRepository.lockAccount(tx, orgId)` before changing any accounting facts. It acquires `FOR UPDATE` and rejects an inconsistent projection.
2. Lock any needed verification/dispatch, reservation, and purchase rows in a consistent order. For later-generation creation, lock the parent verification before the preceding dispatch. Existing generation-1 inserts do not acquire this new parent lock.
3. Resolve idempotency, persist the reservation/ledger/payment/event facts, and call `updateProjection` with the locked account's expected version in the same transaction. A stale version throws `CreditVersionConflictError`; the database also requires version advancement for account updates.
4. Check the resulting invariant before commit. Let errors roll back the transaction; do not catch an invariant/version conflict and commit partial work. Provider calls belong outside this database transaction.

The repository methods are persistence primitives, not implementations of approval, sufficient-credit checks, accounting state machines, payment precedence, or refund calculation. Those belong to later stories. In particular, version checks do not independently establish the ledger/projection invariant if a service writes arbitrary facts without following the transaction contract.

`buildDispatchKey(verificationId, kind, generation = 1)` retains existing keys. Natural identity uniqueness includes verification/kind/generation, with at most one active generation. Inserting generation N > 1 locks the parent and preceding dispatch, requires confirmed rejection or failed delivery, and requires any prior reservation to be released and prior consumption to be reversed. Accepted messages without confirmed failure and ambiguous outcomes cannot gain a successor. No runtime retry path was added.

## Read-only invariant checker

`CreditAccountingRepository.checkInvariant(orgId, tx?)` returns posted balance, held credits, ledger sum, reservation sum, and `consistent`; a missing account returns `undefined`. It evaluates all values in one SQL statement. Aggregate values are returned as strings and compared using bigint to avoid aggregate precision loss. `getSummary` derives `availableCredits = max(postedBalance - heldCredits, 0)` and `debtCredits = max(-postedBalance, 0)`.

Backend operators can inspect all mismatches without changing data:

```sql
SELECT account.org_id,
       account.posted_balance,
       account.held_credits,
       totals.ledger_balance,
       holds.reservation_holds
FROM public.credit_accounts AS account
CROSS JOIN LATERAL (
  SELECT COALESCE(sum(entry.quantity), 0) AS ledger_balance
  FROM public.credit_ledger_entries AS entry
  WHERE entry.org_id = account.org_id
) AS totals
CROSS JOIN LATERAL (
  SELECT COALESCE(sum(reservation.quantity), 0) AS reservation_holds
  FROM public.credit_reservations AS reservation
  WHERE reservation.org_id = account.org_id AND reservation.status = 'held'
) AS holds
WHERE account.posted_balance <> totals.ledger_balance
   OR account.held_credits <> holds.reservation_holds;
```

A mismatch blocks subsequent mutations through `lockAccount`. This story contains no automatic repair or ledger rewrite. A later audited repair must rebuild only projections under the account lock.

| `PAYMOB_CHECKOUT_EXPIRATION_SECONDS`                           | Explicit positive integer required when enabled; no inferred provider default             |

Configured integers are bounded by the PostgreSQL integer range; maximum quantity times unit price must fit that range. Missing pricing variables use approved defaults. Malformed explicitly supplied flags/pricing fail validation even when the feature is disabled; unused provider configuration is ignored while disabled.

Enabled configuration rejects detectable test/live marker conflicts. Live URLs require public HTTPS hostnames and reject IP literals, local/private suffixes, common loopback DNS aliases, placeholder hosts, and test/sandbox hosts. Test mode permits HTTP only for loopback development URLs. Callback paths must be `/api/webhooks/payments/paymob` (a trailing slash is accepted). Live URL checks are syntactic: they do not prove DNS ownership or Paymob integration/account ownership. Actual credentials, callback delivery, integration ownership, and provider expiration limits require the later provider integration/release stories.

## Deployment and recovery

1. Keep `STANDALONE_CREDIT_BILLING_ENABLED=false`. Review preflight totals and resolve any identity anomaly before applying the normal migration runner.
2. Deploy the additive schema before application code that selects the new dispatch generation column. Retain existing Standalone plan/status/period fields; do not convert monthly usage or infer credits.
3. Run the invariant checker and verify only pending zero-balance accounts were added for existing Standalone sources.
4. On application rollback, keep all five tables, dispatch generation, and history protections. Disable later billing entry points; do not drop tables, truncate records, rewind the migration journal, or reverse ledger rows by editing them.
5. For an interrupted transactional migration, fix the cause and rerun the normal runner. Replaying `0032` is safe and does not reset account status, balances, or purchase/ledger facts. Forward recovery uses a new additive migration if an operational schema correction is required.

Approval, free grants, new-organization provisioning changes, credit usage routing, live backfill activation, and Paymob checkout/callback/inquiry execution remain in their respective later stories. Production readiness is not asserted by this local foundation evidence.
